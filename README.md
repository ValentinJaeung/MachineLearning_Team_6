# 26-2-Team-6 — 비행기 도착 시각 예측

> 아주대학교 인공지능융합학과 · **기계학습기초(AAI332)** 2026-2학기 팀프로젝트 6조

**항공사가 알려주는 도착 시각은 약속이 아니라 계획입니다.**
학습 데이터에서 예정 시각 이내 도착은 **57.3%** 뿐이고, 90%가 지켜지는 지점은
예정 도착 **+73분**입니다. 이 프로젝트는 "내가 원하는 확률로 지켜지는 도착 시각"과,
그 위에서 **마감을 지키는 가장 늦은 편**을 찾아 주는 서비스를 만듭니다.

```
손님이 입력:  노선 · 날짜 · 몇 시까지 도착해야 하는지 · 몇 %로 확실해야 하는지
서비스가 답:  그 마감을 지키는 가장 늦은 편 + 보장 도착 시각 + 결항 위험
```

"안전하려면 첫 비행기를 타라"는 상식이 이미 답을 줍니다. 상식이 계산하지 못하는 것은
**경계** — 약속을 지키면서 가장 늦게 떠날 수 있는 편 — 뿐이고, 그것만 남겼습니다.

## 재현

```powershell
pip install -r requirements.txt
```

```powershell
python run_all.py
```

- `data/` 는 저장소에 없습니다(약 2GB). 1단계가 BTS에서 다시 내려받아 재생성합니다.
- 난수는 전부 `src/config.py` 의 `SEED = 42` 로 고정됩니다.
- 단계별 예상 소요 시간을 먼저 보려면 `python run_all.py --dry-run`
- 일부만 다시 돌리려면 `python run_all.py --from 10` 또는 `--only 8`

```powershell
python src/verify_leakage.py
```

누출 감사 **37항목**을 언제든 다시 돌릴 수 있습니다. 연도 겹침, 결과·사후 컬럼의
모델 유입, 식별자 유입, train 에서만 적합했는지, 정답과 지연 분(分)의 일치까지
기계가 점검하고 하나라도 실패하면 0이 아닌 코드로 종료합니다.

실행 환경: Python 3.15.2 · Windows 11 · 16코어 CPU (GPU 없음).

**여름 3개월로 고정한 이유**는 분할을 연도로 하기 때문입니다. 계절 구성이 다르면

**무작위로 섞지 않는 이유**는 실제 사용 상황이 "과거로 배워 미래를 맞히는" 것이고,
섞으면 같은 날 같은 공항의 다른 편이 학습과 평가에 동시에 들어가 그날의 날씨가
양쪽으로 새기 때문입니다.

## 결과

전부 **val 2025** 기준이고, **test 2026 은 15단계에서 단 한 번만** 열었습니다.

**알고리즘 3종 (동일 분할·동일 지표)**

| 모델 | log loss | Brier | CDF 보정오차 | AUC(15분+) | 적합 시간 |
|---|---|---|---|---|---|
| 다항 로지스틱 | 1.40590 | 0.61329 | 0.00751 | 0.69427 | 141초 |
| XGBoost | 1.40473 | 0.61282 | 0.00654 | 0.69607 | 510초 |
| **MLP (PyTorch)** | **1.40034** | 0.61052 | 0.00789 | **0.70002** | 650초 |

세 모델의 폭이 **0.00556** 뿐입니다. 세 모델을 각각 끝까지 튜닝한 뒤 비교한 결과이고,
깊이·하이퍼파라미터 7종의 폭도 0.00278, 다항 차수와 규제 강도의 폭도 0.00257입니다 —
**알고리즘을 바꿔서 가져올 수 있는 것은 여기까지입니다.**

배포는 XGBoost 입니다. MLP 가 log loss 에서 0.00439 앞서지만, 우리가 먼저 선언한
최종 지표인 CDF 보정오차에서는 XGBoost 가 0.00654 로 가장 좋습니다.

**확률 보정 (12단계)** — 보정 학습 구간을 5가지로 바꿔 비교했습니다.

| 보정 구간 | CDF 보정오차 |
|---|---|
| 보정 없음 | 0.00900 |
| 최근 14일 롤링 | 0.00545 |
| 직전 달 (2025-06) | 0.00395 |
| **작년 같은 세 달 (2024 6–8월)** | **0.00193** |

**"가장 최신"이 정답이 아닙니다.** 월 효과가 연도 효과보다 크기 때문에, 계절 구성이
같은 작년이 직전 달보다 더 가까운 과거입니다.

**test 2026 — 약속 이행률 (최종 지표)**

| 약속한 확률 | 실제 이행률 | 오차 | 평균 보장 지연 |
|---|---|---|---|
| 80% | **83.55%** | +3.55%p | +43.6분 |
| 90% | **91.27%** | +1.27%p | +95.8분 |
| 95% | **95.60%** | +0.60%p | +152.1분 |

세 지점 모두 **약속보다 더 지켜지는 방향**으로만 틀립니다. 보정으로 CDF 오차는
0.01147 → **0.00618** 로 줄었고, log loss 는 1.40962 → 1.41132 로 **오히려 나빠집니다** —
보정은 점수를 올리는 작업이 아니라 약속을 정직하게 만드는 작업입니다.

가장 약한 곳도 기록했습니다: 90% 약속의 이행률이 항공사 **OH 에서 84.6%** (−5.36%p).

**무엇이 도착 시각을 정하는가 (TreeSHAP)**

항공사 0.203 · **출발 시각 0.183** · 출발 공항 0.139 · 도착 공항 0.114 · 도착 시각 0.097 ·
공휴일까지의 거리 0.089 · 요일 0.050 · 시간표 여유 0.033 · 월 0.027 · 도착 혼잡 0.012 ·
거리 0.009 · 예정 비행시간 0.004

같은 편을 **출발 시각만 바꿔** 다시 채점하면: 05시 편의 90% 보장 지연은 **+26분**,
19시 편은 **+102분**. 차이 **76분**입니다. 손님이 실제로 바꿀 수 있는 것이 바로 이것입니다.

**서비스가 상식을 이기는 지점**

"첫 비행기를 타라"는 상식은 90% 마감을 98.2% 지킵니다 — 다만 하루를 통째로 씁니다.
우리 서비스는 같은 마감을 95.0% 지키면서 평균 **481분(8시간) 늦게** 출발합니다.
상식이 계산하지 못하는 것은 이 **경계** 하나뿐이고, 그것만 팝니다.

## 설계 원칙

**1. 임의로 고른 숫자를 두지 않는다.**
원-핫할 공항 수는 학습 연도 누적 운항 95% 지점(367개 중 136개)에서 끊고, 10구간
경계와 분할 연도는 `src/config.py` 한 곳에 적어 모든 단계가 같은 값을 읽습니다.

**2. "달라졌다"의 기준을 숫자를 보기 전에 고정한다.**
같은 설정을 시드만 바꿔 세 번 적합해 잡음을 먼저 재고(sd 0.000125) 그 **2배**
(0.000251)를 임계값으로 씁니다. 사후에 기준을 정하면 아무 숫자나 근거가 됩니다.

**3. 약속한 확률이 실제로 지켜지는지를 최종 지표로 삼는다.**
우리가 파는 것은 확률 그 자체입니다. 다른 점수가 아무리 좋아도 "90%"라고 말한 것이
실제로 85%라면 상품이 거짓말입니다.

**4. 누출이 없다는 것을 글로 주장하지 않는다.**
`src/verify_leakage.py` 가 기계적으로 점검하고, 하나라도 실패하면 0이 아닌 코드로
종료합니다.
