# 비행기 도착 시각 예측 — 기계학습기초(AAI332) 2026-2학기 6조

**항공사가 알려주는 도착 시각은 약속이 아니라 계획입니다.** 예정 시각 이내 도착은
**57.3%** 뿐이고, 90%가 지켜지는 지점은 예정 도착 **+73분**입니다.

이 프로젝트는 도착 시각 하나를 맞히는 대신 **10구간 확률 분포**를 예측합니다.
손님이 **그날이 어떤 날일지 가정**하면 그 조건의 분포를 돌려주고, 거기서
**마감을 지키는 가장 늦은 편**을 찾아 줍니다.

```
손님이 입력:  노선 · 날짜 · 마감 시각 · 요구 확률 + 그날의 가정(기본값 정상일)
서비스가 답:  그 마감을 지키는 가장 늦은 편 + 보장 도착 시각 + 결항 위험
```

## 한눈에 보는 결과

**test 2026 — 약속이 지켜졌는가** *(가정한 유형이 그날의 실제 유형일 때)*

| 약속한 확률 | 실제 이행률 | 오차 | 평균 보장 지연 |
|---|---|---|---|
| 80% | **83.97%** | +3.97%p | +43.9분 |
| **90%** | **91.73%** | +1.73%p | +76.8분 |
| 95% | **95.84%** | +0.84%p | +118.1분 |

세 지점 모두 **약속보다 더 지켜지는 방향**으로만 틀립니다.

**손님에게 묻는 것이 모델을 만지는 것보다 크다** (val 2025)

| | log loss | AUC |
|---|---|---|
| 예약 시점 12변수만 | 1.40473 | 0.69607 |
| **+ 그날의 유형 (손님의 가정)** | **1.34895** | **0.75139** |

알고리즘 세 개를 설정 23종까지 비교해서 얻은 폭이 **0.00601**인데, 손님에게 한 번
물어서 얻은 것이 **0.0558** — **9배**입니다. 그리고 그날의 유형은 예약 시점 정보로
**맞힐 수 없습니다**(최빈값 찍기보다 낮음). 그래서 예측하지 않고 묻습니다.

**서비스가 상식을 이기는 지점**

"첫 편을 타라"는 90% 마감을 98.4% 지킵니다 — 다만 하루를 통째로 씁니다. 우리 답은
같은 마감을 94.9% 지키면서 평균 **532분(8.9시간) 늦게** 출발합니다.

```

│   └── AI_USAGE.md          생성형 AI 사용 내역
├── results/                 모든 수치 (CSV·JSON) — 보고서의 표는 전부 여기서
├── figures/                 그림 (본문 18장 + 진단용)
├── src/                     파이프라인 — 한 단계 = 한 파일
├── run_all.py               전체 실행
├── requirements.txt         실행에 쓴 정확한 버전
└── data/                    저장소에 없음 (약 2GB, 1단계가 재생성)
```

각 스크립트 맨 위 docstring 에 **무엇을 읽어 무엇을 쓰는지와 왜 그렇게 하는지**가
적혀 있습니다. 그것이 이 프로젝트의 설계 문서입니다.

**파이프라인**

```
[재료]     1 수집 → 2 정제·10구간 라벨 → 3 시간표 파생 변수 → 6 그날의 유형
[데이터셋]  7 결합·연도 분할 → 8 EDA(설정값 확정) → 9 전처리 두 벌 → 누출 감사
[모델링]   11 모델 3종 (+ 다항·규제 비교) → 12 확률 보정 → 13 해석
          → 14 가정 입력을 받는 최종 모델
[서비스]   15 서비스 평가 (test 2026, 한 번만) → 16 데모 데이터
```

## 데이터

| | |
|---|---|
| 출처 | 미국 교통통계국(BTS) On-Time Performance — **퍼블릭 도메인**, 개인정보 없음 |
| 범위 | 2021–2026년 **6·7·8월**, 미국 국내선, **10,810,813편** |
| 분할 | train 2022–24 (5,408,935) / val 2025 (1,845,381) / test 2026 (1,847,936) |
| 모델 입력 | 예약 시점 **12개** + 손님이 가정하는 **그날의 유형 2칸** |
| 정답 | `y_class` — 10구간 (≤0 / 0–15 / … / 300분+ / 미도착) |

**여름 3개월만 쓰는 이유**는 계절마다 늦는 이유가 다르기 때문입니다 — 여름은 뇌우와
혼잡, 겨울은 제설과 결빙입니다. 한 학기 안에 전부 제대로 다루기 어려워 범위를 좁혔고,
**다른 계절은 같은 파이프라인에 데이터만 추가하면 되는 확장 지점**입니다.

**무작위로 섞지 않는 이유**는 실제 사용 상황이 "과거로 배워 미래를 맞히는" 것이고,
섞으면 같은 날 같은 공항의 다른 편이 학습과 평가에 동시에 들어가 그날의 날씨가
양쪽으로 새기 때문입니다.

## 설계 원칙

**1. 임의로 고른 숫자를 두지 않는다.**
원-핫할 공항 수는 학습 연도 누적 운항 95% 지점(367개 중 136개)에서 끊고, 10구간
경계와 분할 연도는 `src/config.py` 한 곳에 적어 모든 단계가 같은 값을 읽습니다.

**2. "달라졌다"의 기준을 숫자를 보기 전에 고정한다.**
같은 설정을 시드만 바꿔 세 번 적합해 잡음을 먼저 재고(sd 0.000152) 그 **2배**
(0.000304)를 임계값으로 씁니다. 사후에 기준을 정하면 아무 숫자나 근거가 됩니다.
모델·지표마다 잡음의 크기가 달라서, 비교하는 칸마다 그쪽의 산포를 따로 재서 씁니다
(보정오차의 재현성은 모델에 따라 **51배** 차이가 납니다).

**3. 약속한 확률이 실제로 지켜지는지를 최종 지표로 삼는다.**
우리가 파는 것은 확률 그 자체입니다. 다른 점수가 아무리 좋아도 "90%"라고 말한 것이
실제로 85%라면 상품이 거짓말입니다.

**4. 누출이 없다는 것을 글로 주장하지 않는다.**
`src/verify_leakage.py` 가 기계적으로 점검하고, 하나라도 실패하면 0이 아닌 코드로
종료합니다.
