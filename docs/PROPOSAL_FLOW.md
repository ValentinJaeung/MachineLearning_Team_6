# 비행기 도착 시각 예측 — 진행 계획 제안


## 1. 우리가 만드는 것

### 한 줄로

항공사가 알려주는 도착 시각은 "그 시각까지 도착할 확률"이 생각보다 낮기 때문에 "내가 원하는 확률(예: 90%)로 지켜지는 도착 시각"을 알려주는 서비스를 설계.

### 쉽게 말하면

비행기 표를 보면 이렇게 쓰여 있습니다.

```
17:00 출발  →  19:00 도착
```

그런데 이 "19:00 도착"은 **약속이 아니라 계획**입니다. 실제로는 19:00보다 늦게 도착하는 날이 많습니다.

문제는 손님이 그걸 모른 채 계획을 세운다는 겁니다.

```
"20:00에 회의가 있으니까, 19:00 도착이면 1시간 여유네. 괜찮겠지."
```

이 계산이 틀렸습니다. 19:00은 절반 정도만 맞는 숫자이기 때문입니다.

우리가 하려는 건 이렇게 바꿔주는 것입니다.

```
20:00 회의를 90% 확률로 지키려면 16:00에 타는 편이 마지막임
```

### 누구를 위한 서비스인가

| | |
|---|---|
| **사용자** | 도착한 다음에 **미룰 수 없는 약속**이 있는 사람 (회의 · 결혼식 · 공연 · 따로 예약한 환승 · 마중) |
| **쓰는 시점** | **예약하기 직전** — 아직 "다른 편을 고를" 수도 있고 "약속 시간을 바꿀" 수도 있는 유일한 순간 |
| **입력** | ① 어느 노선 ② 어느 날짜 ③ **몇 시까지 도착해야 하는지** ④ **몇 %로 확실해야 하는지**(기본 90%) |
| **출력** | **그 마감을 지키는 가장 늦은 편** + 그 편의 보장 도착 시각 + 결항 위험 + 후보 편 목록 |

### 왜 "가장 늦은 편"인가

"안전하게 가려면 첫 비행기를 타라"는 건 누구나 아는 사실

어려운 건 **경계를 찾는 일**

```
너무 늦은 편  → 약속을 놓칠 수 있음
너무 이른 편  → 하루를 통째로 버림
     ↑
우리가 찾는 건 이 사이의 마지막 안전한 편
```

**"약속을 지키면서 가장 늦게 출발할 수 있는 편"**

## 2. 무엇을 예측하는가 — "하나의 숫자"가 아니라 "분포"

### 흔한 방식과 우리 방식

**흔한 방식**: "이 비행기 지연될까요?" → 예 / 아니오

이게 안 되는 이유가 있습니다. **"늦었다"의 기준이 사람마다 다릅니다.**

```
A씨: 18:00까지 가야 함  →  18:10 도착은 실패
B씨: 21:00까지 가야 함  →  18:10 도착은 대성공
```

같은 비행기, 같은 결과인데 한 사람에게는 실패고 한 사람에게는 성공입니다.
"지연 예상"이라는 한 마디로는 두 사람에게 같은 답밖에 줄 수 없습니다.

**우리 방식**: 비 올 확률 예보처럼, **구간별 확률을 전부** 내놓습니다.

### 10개의 구간

| 번호 | 구간 | 뜻 |
|---:|---|---|
| 0 | ≤ 0분 | 정시 또는 일찍 도착 |
| 1 | 0–15분 | 조금 늦음 |
| 2 | 15–30분 | |
| 3 | 30–60분 | |
| 4 | 60–90분 | |
| 5 | 90–120분 | |
| 6 | 120–180분 | |
| 7 | 180–300분 | 많이 늦음 |
| 8 | 300분 초과 | 심각하게 늦음 |
| 9 | **미도착** | 결항, 또는 회항해서 목적지에 못 감 |

모델은 각 편에 대해 **이 10개 칸의 확률**을 내놓습니다. 예를 들면:

```
0번 60% | 1번 15% | 2번 8% | 3번 7% | 4번 4% | ... | 9번 1%
```

### 이 하나에서 화면의 모든 것이 나옵니다

구간 확률을 앞에서부터 더하면 "몇 분 안에 도착할 확률"이 됩니다.

```
0~1번을 더하면  →  "15분 안에 도착할 확률 75%"
0~3번을 더하면  →  "1시간 안에 도착할 확률 90%"
```

그래서 **거꾸로도 읽을 수 있습니다.**

```
"90%가 되는 지점은 어디?"  →  "1시간"  →  90% 보장 도착 시각 = 예정 도착 + 1시간
9번 칸의 확률               →  결항 위험
```

> **핵심**: 마감 시각과 요구 확률을 **손님에게 넘기고**, 모델은 분포만 만듭니다.
> 그래서 한 번 학습한 모델로 A씨와 B씨에게 **각각 다른 답**을 줄 수 있습니다.



## 3. 변수 설명

### 3-1. 원본 변수 — 데이터에서 그대로 받는 것

미국 교통통계국(BTS)이 공개하는 국내선 운항 기록을 씁니다. 원본에는 컬럼이 100개가 넘는데, 우리는 **세 종류로 나눠서** 씁니다 — 🟢 **A** 예약 시점에 아는 것, 🔴 **B** 결과, 🟡 **C** 사후 정보.

그리고 **A는 다시 둘로 나뉩니다.** 예약 화면에서 손님이 보는 값과, 데이터를 잇기 위한 식별자는
성격이 다릅니다. 식별자는 예약 시점에 확정되지 않은 것도 있어서, 입력 후보로 섞으면 안 됩니다.

#### 🟢 A-1 — 예약 시점에 알 수 있는 것 (**모델 입력 후보**)

| 변수 | 뜻 |
|---|---|
| `Month` | 월 (6 · 7 · 8) |
| `DayOfWeek` | 요일 |
| `CRSDepTime` | **예정** 출발 시각 |
| `CRSArrTime` | **예정** 도착 시각 |
| `Reporting_Airline` | 항공사 |
| `Origin` | 출발 공항 |
| `Dest` | 도착 공항 |
| `Distance` | 비행 거리 |
| `CRSElapsedTime` | **예정** 소요 시간 |

> `CRS`가 붙은 건 전부 **"계획된"** 값입니다. 표를 예약할 때 화면에 보이는 숫자들입니다.

#### 🟢 A-2 — 식별자 (**데이터를 잇는 데만 씀. 입력 아님**)

| 변수 | 뜻 | 어디에 쓰나 | 예약 시점에 아는가 |
|---|---|---|---|
| `FlightDate` | 날짜 | 연도 분할 · 성적표 조인 · 기체의 "그날" 묶기 | ✅ (월·요일만 입력으로 씀) |
| `Flight_Number` | 편명 (예: 1234편) | `flight_key` 생성 | ✅ (번호 자체는 입력 아님) |
| `Tail_Number` | 기체 등록번호 | **작년** 기록에서 하루 운항 사슬 복원 (③) | ❌ **모름** |

**`Tail_Number`는 예약 시점에 알 수 없습니다.** 기체는 편에 소속된 자원이 아니라 운항 당일
스케줄에 따라 배정됩니다. 같은 편명·같은 노선에 한 달간 서로 다른 기체가 열 대 넘게 들어오고,
매일 다른 기체가 들어오는 편도 있습니다. 예약 화면에 기종은 떠도 **기체 번호는 뜨지 않습니다.**

그런데도 쓸 수 있는 이유는 **작년 데이터에서만 쓰기 때문**입니다.

```
작년 기록 (기체 배정이 이미 확정된 과거)
  └ Tail_Number 로 하루 사슬 복원 → day_seq / turnaround_min / prev_delayed / absorbed (③)
      └ 편명·노선 키로 집계 → 성적표 (⑤)
          └ 올해 편에 붙일 때는 flight_key / route_key / group_key 로 조인
                                 ↑ 기체 번호가 아닙니다
```

> **올해 그 편에 어떤 기체가 들어올지는 묻지도, 쓰지도 않습니다.** 묻는 것은 "작년에 이
> 편명·이 노선이 어땠나"뿐이고, 그건 예약 시점에 이미 존재하는 정보입니다.

`Flight_Number`도 같은 성격입니다. 편명은 해마다 다른 노선에 재배정되는 **번호표**라서(② 참조)
그 자체를 입력에 넣으면 의미 없는 고유번호를 외우게 됩니다. 키를 만드는 재료로만 씁니다.

> ⚠️ **식별자를 입력에 넣으면 안 되는 두 번째 이유:** `Tail_Number` + `FlightDate` + 시간표
> 조합은 **특정 운항 1편을 지목**합니다. 학습 중에는 정답이 붙어 있으니, 모델이 "이 조합 = 이
> 결과"를 외우는 경로가 생깁니다. 예약 시점 가용성과 별개로, 식별자는 그 자체로 위험합니다.

#### 🔴 B그룹 — 결과 (**정답 만들기용. 입력으로 쓰면 안 됨**)

| 변수 | 뜻 |
|---|---|
| `ArrDelay` | 실제 도착 지연 (분) |
| `Cancelled` | 결항했는지 |
| `Diverted` | 회항했는지 |
| `DivReachedDest` | 회항 후 목적지에 도달했는지 |
| `DivArrDelay` | 회항한 편의 최종 도착 지연 |

> 이걸로 **10구간 정답**을 만듭니다. 회항했지만 목적지에 도착한 편은 손님 입장에서 "다른 사건"이 아니라 **아주 늦은 도착**이므로, `DivArrDelay`를 써서 지연 구간에 넣습니다.
>
> ⚠️ 이 변수들은 **비행기가 끝난 뒤에야** 생깁니다. 예약 시점에는 존재하지 않으므로 입력에 넣으면 "미래를 보고 예측하는" 반칙이 됩니다.

#### 🟡 C그룹 — 사후 정보 (**"그날의 상태"를 만드는 재료. 입력 아님**)

| 변수 | 뜻 |
|---|---|
| `CarrierDelay` | 항공사 책임 지연 (분) |
| `WeatherDelay` | 날씨 책임 지연 |
| `NASDelay` | 관제·공역 혼잡 책임 지연 |
| `SecurityDelay` | 보안 책임 지연 |
| `LateAircraftDelay` | 앞 비행기가 늦어서 생긴 지연 |
| `CancellationCode` | 결항 사유 |
| `DepDelay` | 실제 출발 지연 |
| `DepTime` · `ArrTime` | 실제 출발 · 도착 시각 |
| `ActualElapsedTime` · `AirTime` | 실제 소요 시간 · 공중 비행 시간 |
| `TaxiOut` · `TaxiIn` | 활주로 이동 시간 |

> 이것들로 **"그날 그 공항이 어떤 상태였나"** 를 만듭니다. 이 변수 자체는 입력에 안 들어가고, 여기서 만든 **요약값만** 들어갑니다.

### 3-2. 우리가 새로 만드는 변수

원본을 그대로 쓰면 모델이 이해하지 못하거나, 중요한 정보가 숨어 있어서 안 보입니다. 그래서 만듭니다.

#### ① 시각을 숫자로 바꾼 변수

| 만들 변수 | 만드는 법 | 왜 필요한가 |
|---|---|---|
| `crs_dep_min` | 예정 출발을 **자정부터 몇 분**으로 | `1435`라는 표기는 숫자가 아님. `1359`와 `1400`은 1분 차이인데 숫자로는 41 차이 |
| `crs_arr_min` | 예정 도착을 같은 방식으로 | 같음 |
| `crs_dep_hour` | 예정 출발 **시(時)** | "몇 시 편인가"가 가장 중요한 정보일 것으로 예상 |
| `crs_arr_hour` | 예정 도착 **시(時)** | 같음 |

#### ② 이름표 변수 (키) — "같은 비행기"를 찾기 위한 것

작년 기록을 올해 편에 붙이려면 **"같은 편"을 알아보는 이름표**가 필요합니다. 그런데 이름표는 세 가지 넓이로 만듭니다.

| 만들 변수 | 만드는 법 | 얼마나 좁은가 |
|---|---|---|
| `flight_key` | 항공사 + 편명 + 출발공항 + 도착공항 | **가장 좁음** — "델타 4628편, 앨버커키→덴버" |
| `route_key` | 항공사 + 출발공항 + 도착공항 | 중간 — "델타의 앨버커키→덴버 노선" |
| `group_key` | 항공사 + 출발공항 + 예정 출발 시 | **가장 넓음** — "델타가 앨버커키에서 오후 2시대에 띄우는 편" |

**왜 세 개나 만드나.** 항공사는 **편명을 해마다 다른 노선에 다시 나눠줍니다.** 번호표일 뿐이라서요.

```
"델타 4628편"
  작년:  하트포드 → 디트로이트
  올해:  앨버커키 → 뉴욕        ← 번호만 같고 완전히 다른 비행
```

그래서 가장 좁은 이름표(`flight_key`)로 작년 기록을 찾으면 **상당수가 안 찾아집니다.**

**해결: 좁은 쪽부터 찾고, 없으면 넓은 쪽으로 양보합니다.**

```
flight_key 로 찾아본다   → 있으면 그 값 사용
  없으면 route_key      → 있으면 그 값 사용
    없으면 group_key    → 있으면 그 값 사용
      그래도 없으면      → 전체 평균 사용
```

그리고 **"몇 번째에서 찾았는지"를 `substitute_level`(0~3)로 함께 기록**합니다. 나중에 "정확하게 찾은 행만 봐도 결과가 같은가"를 확인할 수 있습니다.

> 마지막에 전체 평균을 쓰는 이유: 작년에 없던 **새 노선**은 매년 생깁니다. 그 편에도 답을 줘야 하는데, 빈칸으로 두면 모델이 "빈칸 = 새 노선"이라는 엉뚱한 패턴을 배웁니다. 0으로 채우면 "한 번도 안 늦은 완벽한 편"이라고 거짓말이 됩니다. **평균은 "모른다"를 어느 쪽으로도 기울이지 않는 중립값입니다.**

#### ③ 연결편 변수 — "앞 비행기가 늦으면 이 비행기도 늦는다"

비행기는 하루에 여러 번 뜹니다. 같은 기체가 아침에 A→B, 다음에 B→C, 또 C→D를 돕니다.

```
기체 N123AB 의 하루
  06:00 A → B  (40분 늦게 도착)
  08:25 B → C  ← 이 편은 출발 전부터 이미 불리함
  11:00 C → D  ← 지연이 계속 따라감
```

손님이 보는 "08:25 출발"에는 이 정보가 없습니다. 그래서 만듭니다.

| 만들 변수 | 뜻 | 쓰는 원본 |
|---|---|---|
| `day_seq` | 그 기체의 그날 **몇 번째** 비행인가 | `Tail_Number`, `FlightDate`, `crs_dep_min` |
| `is_first_flight` | 그날 첫 비행인가 (첫 편은 밤새 쉬었으므로 유리할 것) | `day_seq` |
| `turnaround_min` | 앞 비행 예정 도착 → 이 편 예정 출발까지의 **쉬는 시간** | `crs_arr_min`, `crs_dep_min` |
| `prev_delayed` | 앞 비행이 15분 이상 늦게 도착했나 | `ArrDelay` (앞 행) |
| `absorbed` | 앞 비행이 늦었는데 **이 편은 정시에 떴나** | `prev_delayed`, `DepDelay` |

**`absorbed`가 핵심 아이디어입니다.** 앞 비행이 늦게 들어왔는데도 정시에 출발했다면, 그 기체·항공사·공항에 **지연을 삼킬 여력**이 있다는 뜻입니다.

> ⚠️ 중요: 앞 비행이 **늦지 않았으면** `absorbed`는 "빈칸"으로 둡니다. 삼킬 지연이 없었으니 "삼켰다/못 삼켰다"를 말할 수 없습니다. 이걸 0으로 채우면 **"시험을 안 본 사람"을 "시험에서 틀린 사람"으로 집계**하게 됩니다.
>
> `turnaround_min`은 **예정 시각**으로 계산합니다. 예약 시점에 알 수 있는 건 시간표뿐이고, 재려는 것도 "항공사가 설계한 여유"입니다.

#### ④ 공항-날짜 변수 — "그날 그 공항이 무너졌나"

연결편은 "이 비행기 한 대"의 사정입니다. 그런데 **공항 전체가 무너지는 날**이 있습니다. 폭풍이 오거나 관제가 막히면 그 공항의 **모든 편**이 늦습니다.

(출발공항, 날짜) 한 칸에 하나씩 만듭니다.

| 만들 변수 | 뜻 | 쓰는 원본 |
|---|---|---|
| `n_flights` | 그날 그 공항에서 뜬 편 수 | — |
| `mean_dep_delay` | 그날 그 공항의 **평균 출발 지연** | `DepDelay` |
| `fail_rate` | 그날 그 공항 편들의 실패 비율 | 정답 라벨 |
| `bad_day` | 그날이 그 공항의 **나쁜 날**인가 | `mean_dep_delay` |

**`bad_day`는 "상대적으로" 정합니다.** 그 공항, 그 연도 안에서 **평균 출발 지연이 상위 10%에 드는 날**을 나쁜 날로 봅니다.

왜 상대 기준인가:

```
평균 출발 지연 30분인 날
  한가한 공항에서는  →  최악의 날
  원래 붐비는 공항에서는 →  평범한 날
```

"30분 넘으면 나쁜 날"처럼 **하나의 기준**을 쓰면, 붐비는 공항은 1년의 절반이 나쁜 날이 되고 한가한 공항은 거의 없게 됩니다. 그러면 이 변수는 "그날이 나빴나"가 아니라 **"이 공항이 원래 붐비나"** 를 재게 되고, 그건 공항 이름이 이미 알려주는 정보입니다.

**연도별로도 따로 자릅니다** — 해마다 전체 지연 수준이 달라지므로, 묶어서 자르면 특정 연도에 나쁜 날이 몰립니다.

#### ⑤ 과거 이력 변수 — "이 편의 작년 성적표"

③④에서 만든 것을 **이름표(키)별로 모아** 성적표를 만듭니다.

| 만들 변수 | 뜻 | 재료 |
|---|---|---|
| `A_absorb_rate` | 앞 비행이 늦었을 때 **정시 출발에 성공한 비율** | `absorbed` |
| `B1_turnaround_mean` | 평균 쉬는 시간 (분) | `turnaround_min` |
| `B2_day_seq_mean` | 하루 중 평균 몇 번째 비행인가 | `day_seq` |
| `B3_first_flight_rate` | 그날 첫 편이었던 비율 | `is_first_flight` |
| `C_bad_day_rel_fail` | **나쁜 날에, 같은 공항 다른 편들보다 잘 버텼나** | `bad_day`, `fail_rate` |

**`C`가 가장 공들인 변수입니다.** 나쁜 날의 "그냥 실패율"을 쓰면 안 됩니다. 그건 "나쁜 날이 많은 공항에 있나"를 재는 것이고, 공항 이름이 이미 아는 정보입니다.

그래서 **빼서** 만듭니다.

```
C = (그 편이 실패했나)  −  (그날 그 공항 전체의 실패율)

음수면 → 공항이 무너진 날에도 이 편은 비교적 잘 버텼다
양수면 → 공항보다 더 나빴다
```

같은 날 같은 공항의 다른 편들이 기준선이 되니까, 날씨·관제 같은 공통 요인이 전부 상쇄되고 **그 편 고유의 튼튼함만** 남습니다.

##### 표본이 적은 편을 그대로 믿지 않습니다 (평활)

문제가 하나 있습니다. **어떤 편은 작년에 딱 한 번만 시험을 봤습니다.**

```
작년에 "앞 비행이 늦은" 상황을 1번만 겪은 편
  그 1번에 정시 출발 성공  →  흡수율 100%
  그 1번에 실패           →  흡수율 0%
```

동전 한 번 던진 결과로 "이 편은 완벽하다 / 최악이다"가 결정됩니다. 그건 정보가 아니라 잡음입니다.

**해결: 표본이 적으면 "한 단계 넓은 이름표의 값" 쪽으로 끌어당깁니다.**

```
         (관측 횟수 × 그 편의 값)  +  (k × 넓은 이름표의 값)
보정값 = ───────────────────────────────────────────────
                      관측 횟수 + k
```

- 관측이 **많으면** → 그 편의 값을 거의 그대로 믿음
- 관측이 **적으면** → 넓은 이름표의 값 쪽으로 당겨짐
- 관측이 **0이면** → 수식이 자동으로 넓은 이름표의 값이 됨

`k`는 **경험적 베이즈**로 데이터에서 정합니다. 아이디어는 이렇습니다.

```
편들 사이에 보이는 흩어짐  =  진짜 실력 차이  +  표본이 작아서 생긴 잡음
                                               ↑ 이건 계산할 수 있음
→ 빼면 "진짜 실력 차이"가 남고, 둘의 비율이 k
```

잡음이 실력 차이보다 크면 `k`가 커지고(= 넓은 쪽을 더 믿어라), 실력 차이가 뚜렷하면 작아집니다. **임의로 고르지 않습니다.**

> 비율 변수(`A`, `C`)에만 적용합니다. `B`는 "쉬는 시간 61분" 같은 연속값이라 한 번만 재도 극단으로 튀지 않습니다.

#### ⑥ 그날의 유형 변수 (시나리오)

C그룹(지연 원인별 분) 변수를 써서, **(공항, 날짜) 한 칸이 어떤 종류의 날이었나**를 몇 가지 유형으로 나눕니다.

```
평상일          특별한 일이 없던 날
항공사 귀책일    항공사 자체 문제가 지연의 대부분이었던 날
연결편 붕괴일    앞 비행기 지연이 줄줄이 번진 날
공역 혼잡일      관제·항로 혼잡이 주된 원인이었던 날
날씨일          날씨가 주된 원인이었던 날
```

**중요한 설계 두 가지:**

**(1) "그 편"이 아니라 "그 공항-그 날짜"에 유형을 붙입니다.** 편 하나하나에 "이 편은 날씨 때문에 늦었다"를 붙이면, **결과를 보고 결과를 설명하는** 꼴이 됩니다. 늦은 편만 원인이 기록되므로 늦지 않은 편과 비교가 안 됩니다.

**(2) 출발 공항과 도착 공항 둘 다 봅니다.** 출발지가 멀쩡해도 도착지가 무너지면 늦습니다.

##### 비지도 학습으로 타당성을 확인합니다

유형을 **규칙으로** 나누긴 했지만, "그 구분이 데이터에 실제로 존재하는가"는 따로 확인해야 합니다.

```
지연 원인 구성비 등을 PCA 로 차원 축소
   → 군집(clustering)으로 자연스럽게 몇 개 덩어리로 나뉘는지 봄
   → 그 덩어리가 우리 규칙 유형과 일치하는지 교차표·일치도 지표로 비교
```

일치하면 "우리가 손으로 정한 유형이 데이터에도 있다"는 근거가 됩니다.

##### ⚠️ 시나리오는 **예측이 아니라 가정**입니다

예약 시점에는 **그날이 어떤 날이 될지 알 수 없습니다.** 그래서 모델이 유형을 맞히게 하지 않습니다.

대신 **손님이 가정을 고릅니다.**

```
"평상일이라면 → 90% 보장 도착 몇 시?"
"날씨가 나쁜 날이라면 → 몇 시?"
```

중요한 약속일수록 나쁜 쪽 가정에 맞추면 됩니다. **가정이 바뀌면 "가장 늦은 편"이라는 답 자체가 바뀝니다.**

#### ⑦ 정답 변수

| 만들 변수 | 뜻 | 재료 |
|---|---|---|
| `y_class` | **10구간 중 어디** (0~9) | `ArrDelay`, `Cancelled`, `Diverted`, `DivReachedDest`, `DivArrDelay` |

## 4. 분석 단계

### 전체 그림

```
[재료 모으기]
 1. 데이터 수집
 2. 정제 + 시각 변환 + 이름표 만들기
 3. 연결편 잇기          ┐
 4. 공항-날짜 상태 집계   ├→ 5. 키별 성적표 만들기
                        ┘
 6. 그날의 유형 만들기 (+ 비지도 학습으로 타당성 확인)

[데이터셋 만들기]
 7. 하나의 표로 합치고 연도로 나누기
 8. EDA — 데이터를 보고 설정값을 정하고, 지연 구조를 기술
 9. 전처리 — 모델이 먹을 수 있는 형태로

[모델링]
10. 변수 선택 — 어떤 변수가 실제로 도움이 되는가
11. 모델 3종 비교 → 하나 선택
12. 확률 보정 — 말한 확률이 실제와 맞게
13. 모델 해석 (what-if)
14. 시나리오별 모델

[서비스]
15. 서비스 평가 — 약속을 지켰나
16. 데모 페이지
```

---

### 1단계 — 데이터 수집

| | |
|---|---|
| **하는 일** | BTS 운항 기록을 월 단위로 받아 저장 |
| **범위** | **2021~2026년, 6·7·8월만** (여름) |
| **쓰는 변수** | 원본 전체에서 필요한 컬럼만 골라 받음 (A·B·C 그룹) |

**왜 여름만?** 데이터를 **연도로 나눠서** 학습/검증/평가에 쓸 계획입니다. 그러려면 세 묶음의 **계절 구성이 같아야** 합니다. 전 계절을 받아놓고 연도로 나누면, 성능 차이가 "연도 차이"인지 "계절 차이"인지 구분이 안 됩니다. 여름 3달로 고정하면 **비교할 축이 하나만** 남습니다.

**왜 2021년도?** 2021년은 학습에 안 씁니다. "작년 성적표"를 만드는 **재료**로만 씁니다. 2022년 편에 붙일 작년이 2021년이니까요.

---

### 2단계 — 정제 + 시각 변환 + 이름표

| | |
|---|---|
| **하는 일** | 시각을 숫자로 바꾸고, 이름표 3종을 만들고, 10구간 정답을 만듦 |
| **쓰는 변수** | `CRSDepTime` `CRSArrTime` / `Reporting_Airline` `Flight_Number` `Origin` `Dest` / B그룹 전체 |
| **만드는 변수** | `crs_dep_min` `crs_arr_min` `crs_dep_hour` `crs_arr_hour` / `flight_key` `route_key` `group_key` / `y_class` |

**이상치는 지우지 않습니다.** 극단적으로 늦은 편(300분 초과, 미도착)이 바로 우리가 팔려는 물건입니다. **"90% 보장 시각"은 분포의 꼬리에서 결정**되므로, 꼬리를 자르면 보장 시각이 낙관적으로 틀어지고 약속이 깨집니다.

---

### 3단계 — 연결편 잇기

| | |
|---|---|
| **하는 일** | 같은 기체의 **직전 비행**을 각 편에 연결 |
| **쓰는 변수** | `Tail_Number` `FlightDate` `crs_dep_min` `crs_arr_min` `Origin` `Dest` `Cancelled` `ArrDelay` `DepDelay` |
| **만드는 변수** | `day_seq` `is_first_flight` `turnaround_min` `prev_delayed` `absorbed` |

기체 → 날짜 → 예정 출발 순으로 줄 세우면 바로 앞 행이 직전 비행입니다. 다만 **네 조건을 모두** 만족할 때만 연결로 인정합니다.

```
① 같은 기체인가
② 같은 날인가           (어제 밤 편은 밤새 쉬었으므로 지연이 안 번짐)
③ 앞 비행 도착공항 == 이 편 출발공항   (안 맞으면 중간에 기록 없는 이동이 있었음)
④ 앞 비행이 결항이 아닌가  (결항된 비행엔 도착 지연이 없음)
```

### 4단계 — 공항-날짜 상태 집계

| | |
|---|---|
| **하는 일** | (출발공항, 날짜)마다 그날의 상태를 요약 |
| **쓰는 변수** | `Origin` `FlightDate` `DepDelay` `Cancelled` `y_class` |
| **만드는 변수** | `n_flights` `mean_dep_delay` `fail_rate` `bad_day` |

`mean_dep_delay`는 결항 편을 빼고 계산합니다(뜨지 않은 비행엔 출발 지연이 없음). `fail_rate`는 결항을 넣고 계산합니다(정답이 결항을 실패로 세니까). **쓰임이 다르므로 분모를 각각 맞춥니다.**

---

### 5단계 — 키별 성적표 만들기

| | |
|---|---|
| **하는 일** | 3·4단계 결과를 이름표별로 모아 "작년 성적표"를 만듦 |
| **쓰는 변수** | `absorbed` `turnaround_min` `day_seq` `is_first_flight` / `bad_day` `fail_rate` / `y_class` / 키 3종 |
| **만드는 변수** | `A_absorb_rate` `B1_turnaround_mean` `B2_day_seq_mean` `B3_first_flight_rate` `C_bad_day_rel_fail` |

**철칙: Y년 성적표는 Y−1년 데이터만으로 만듭니다.**

```
2022년 편의 성적표  ←  2021년 여름만 보고 만듦
2025년 편의 성적표  ←  2024년 여름만 보고 만듦
```

타깃 연도의 데이터는 한 줄도 들어가지 않습니다. 예약 시점에 실제로 알 수 있는 정보만 쓰는 것입니다.

성적표는 **이름표 3종 × 연도별**로 각각 만듭니다. `A`와 `C`에는 평활(⑤ 참조)을 적용합니다.

---

### 6단계 — 그날의 유형 만들기

| | |
|---|---|
| **하는 일** | (공항, 날짜)마다 유형을 붙이고, 비지도 학습으로 타당성 확인 |
| **쓰는 변수** | `CarrierDelay` `WeatherDelay` `NASDelay` `SecurityDelay` `LateAircraftDelay` `CancellationCode` `TaxiOut` `TaxiIn` |
| **만드는 변수** | `scenario_type` (5유형) |
| **비지도 학습** | PCA로 차원 축소 → 군집 → 규칙 유형과 교차 비교 |

편수가 너무 적은 날은 제외합니다 — 하루 한두 편으로는 "그날 공항이 어땠나"를 말할 수 없습니다.

---

### 7단계 — 하나의 표로 합치고 연도로 나누기

| | |
|---|---|
| **하는 일** | 편 단위 행에 성적표를 붙이고(이름표 폴백), 연도로 분할 |
| **쓰는 변수** | A-1 전체 + A-2(조인용) + 키 3종 + 성적표 5개 + `y_class` |
| **만드는 변수** | `substitute_level` (몇 번째 이름표에서 찾았는지) |

```
학습(train)   2022 · 2023 · 2024     (성적표는 2021 · 2022 · 2023 에서)
검증(val)     2025                   (성적표는 2024 에서)
평가(test)    2026                   (성적표는 2025 에서)
```

**무작위로 섞지 않고 연도로 나눕니다.** 실제 사용 상황이 "과거로 배워 미래를 맞히는" 것이기 때문입니다. 무작위로 섞으면 **같은 날 같은 공항의 다른 편**이 학습과 평가에 동시에 들어가서, 그날의 날씨가 양쪽에 새어 들어갑니다.

> `train`이 3년이지만 **각 연도가 서로 다른 작년에서 성적표를 받습니다.** 3년을 한 덩어리로 묶어 성적표를 만들면 2022년 편이 2023년을 보게 됩니다.

### 8단계 — EDA (탐색적 데이터 분석)

| | |
|---|---|
| **하는 일** | 데이터를 들여다보며 ① **뒤 단계가 쓸 설정값**을 정하고 ② **지연의 구조를 기술**함 |
| **보는 범위 — ① 설정값** | **학습 연도(2022~24)와 그 성적표 연도(2021~23)만.** 검증·평가 연도는 보지 않음 |
| **보는 범위 — ② 구조 기술** | 전 기간. 사후 정보의 기술통계일 뿐이므로 **설정값·변수 선택에는 쓰지 않음** |

**왜 안 보나:** 평가용 데이터의 분포를 눈으로 본 것만으로도 선택에 영향을 줍니다("평가 연도는 8월이 좋네, 그럼 월 변수를 이렇게 쓰자"). 그게 반칙입니다.

**정할 것:**

| 설정값 | 정하는 방법 | 어디에 쓰이나 |
|---|---|---|
| 평활 강도 `k` | 경험적 베이즈 — 키별 비율의 흩어짐을 **표본 잡음 몫**과 **진짜 차이 몫**으로 분해해 그 비로 정함 (⑤ 참조) | 5단계 |
| 원-핫할 공항 개수 | 공항별 누적 운항량 비중을 보고, 수익이 꺾이는 지점 | 9단계 |
| **나쁜 날 기준** | 공항별 지연 분포를 보고, 공통 절대값이 아니라 **공항·연도 안의 상대 분위**로 정함 (④ 참조) | 4단계 |
| **성적표 조인 키 구성** | 이름표 넓이별 매칭률을 보고 **좁은 쪽 → 넓은 쪽 계층 축소**를 채택. 몇 번째에서 찾았는지도 함께 기록 (② 참조) | 5단계 |

> 네 개 모두 **데이터를 보고 정합니다.** 임의로 고른 숫자가 없다는 것이 이 단계의 결과물입니다.

**볼 것:**

| 보는 것 | 알고 싶은 것 |
|---|---|
| 10구간 분포 | "정시 도착"이 실제로 몇 %인가 — **서비스의 첫 문장** |
| 출발 시각별 실패율 | 하루 중 언제가 위험한가, 그 모양이 직선인가 |
| 공항-날짜 지연 분포 | 공항마다 "나쁜 날" 기준이 얼마나 다른가 |
| 이름표별 매칭률 | 작년 기록이 얼마나 붙는가 |
| 키별 관측 횟수 분포 | 평활이 얼마나 필요한가 |
| 변수 간 상관 | 겹치는 변수가 있는가 |
| 변수와 정답의 관계 | 어떤 변수가 갈라 보이는가 |
| 하루 후보 편수 | 손님에게 제시할 선택지가 몇 개나 되는가 — **서비스 설계** |

**원인 구성도 봅니다 (🟡 C그룹 사용):**

지연 원인별 분(分)과 취소 사유를 써서 **"왜 실패하는가"** 를 기술합니다. 이 변수들은 사후 정보라
모델 입력에 못 들어가지만, **설계 판단의 배경**이 되고 보고서의 서술 재료가 됩니다.

| 보는 것 | 알고 싶은 것 |
|---|---|
| 전체 지연의 원인별 구성 | 가장 큰 원인이 무엇인가 — 연결편 변수(③)를 만든 근거 |
| 출발 시각별 원인 구성 | 시각이 바뀌면 **실패의 종류**도 바뀌는가 |
| 연도별 추세 | 기간 안에서 실패율과 원인 비중이 움직이는가 — 결과 해석 범위 |
| 규칙 유형 vs 군집 | 손으로 정한 유형이 데이터에도 있는가 (⑥ 참조) |

**출발 시각과 구간 순번은 같은 것을 두 번 세는 것일 수 있습니다.** 이른 편은 그날 첫 구간이라
물려받을 지연이 없고, 늦은 편은 이미 여러 번 날아온 기체를 받습니다. 두 변수를 각각 독립적으로
넣으면 같은 기제를 중복 계상합니다.

> ⚠️ **구조 기술은 전 기간을 보므로, 여기서 나온 관찰을 그대로 설계 근거로 쓰면 안 됩니다.**
> 변수를 넣고 빼는 판단으로 이어질 관찰은 **학습 연도만으로 다시 확인한 뒤** 채택합니다. 구조
> 기술의 역할은 "무엇을 확인해 볼 가치가 있는가"를 좁히는 것까지입니다.

### 9단계 — 전처리

| | |
|---|---|
| **하는 일** | 같은 변수에서 **두 가지 형태**를 만듦 |
| **쓰는 변수** | 입력 후보 전체 |

| | 선형 모델용 | 트리 모델용 |
|---|---|---|
| 범주형 (항공사·공항·요일·월) | **원-핫** (0/1 열로 펼침) | 그대로 (범주형 타입) |
| 시각 | **원-핫** | 숫자 그대로 |
| 수치형 | 결측 채우기 + 표준화 | 손대지 않음 |

**왜 두 벌인가.** 모델이 먹을 수 있는 형태가 다릅니다.

- 선형 모델은 "ATL"을 이해 못 합니다. 공항에 1·2·3 번호를 매기면 **"ATL과 DEN 사이에 DFW가 있다"는 거짓 순서**가 생깁니다. 그래서 원-핫이 필요합니다.
- 트리는 범주를 그대로 쓸 수 있습니다. 원-핫으로 펼쳐주면 오히려 손해입니다 — 100개 열에 흩어진 공항 정보를 한 번에 못 쓰고 100번 나눠야 합니다.

> 두 모델을 비교하는 것이 목표인데, **각 모델에 불리한 형태로 주면 비교가 "모델 비교"가 아니라 "형태 비교"** 가 됩니다.

**시각은 선형 쪽에서만 원-핫입니다.** 하루 중 실패율이 올라갔다 꺾여 내려오는 모양이라면, 숫자 한 칸으로는 **직선 하나**밖에 그을 수 없습니다. 트리는 같은 변수를 반복해서 나눌 수 있어 꺾인 모양을 스스로 만듭니다.

**공항은 상위 N개만 원-핫하고 나머지는 "기타"로 묶습니다.** 하루 한두 편짜리 공항은 학습 데이터가 거의 없어서 계수를 추정할 수 없고, 열만 늘어납니다.

> ⚠️ **채우기·표준화에 쓰는 값(중앙값·평균·표준편차)은 학습 데이터에서만 계산합니다.** 검증·평가 데이터는 그 값으로 **변환만** 당하고 다시 계산하지 않습니다. 평가 데이터의 평균을 알고 있다면, 미래 분포를 미리 본 셈입니다.

### 10단계 — 변수 선택 (Feature Selection)

| | |
|---|---|
| **하는 일** | 후보 변수들을 하나씩 넣어보고, **실제로 도움이 되는 것만** 남김 |
| **쓰는 변수** | 기본 입력 + 후보군 전체 |

#### 판정 기준: 상관이 아니라 **기여**

| | |
|---|---|
| ❌ **상관** | "이 변수가 정답과 같이 움직인다" |
| ✅ **기여** | "이 변수를 넣으면 **예측이 실제로 좋아진다**" |

둘은 다릅니다. 정답과 같이 움직이는 변수여도, 이미 있는 다른 변수가 그 정보를 **똑같이 담고 있으면** 넣어도 아무 변화가 없습니다. 심지어 **나빠질 수도** 있습니다(잡음만 추가).

> 쉽게 말하면 — 농구팀에 **키 큰 선수**를 한 명 더 넣는 건 좋습니다. 그런데 이미 키 큰 선수가 5명 있으면, 6번째 장신은 아무것도 바꾸지 않습니다. **그 선수가 좋은 선수인지가 아니라, 우리 팀에 보탬이 되는지를 봐야 합니다.**

### 11단계 — 모델 3종 비교

| | |
|---|---|
| **하는 일** | 세 모델을 **같은 데이터, 같은 지표**로 비교해 하나 선택 |
| **쓰는 변수** | 10단계를 통과한 입력 전체 |

| 모델 | 어떤 모델인가 |
|---|---|
| **다항 로지스틱 회귀** | 가장 단순한 분류 모델. 각 구간의 확률을 직선 조합으로 계산 |
| **XGBoost** | 결정 트리를 수백 개 쌓아 조금씩 보완해가는 모델 |
| **MLP (신경망)** | 딥러닝. 출력층에서 10구간 확률을 한 번에 냄 |

**세 모델이 전부 10개 구간의 확률을 내놓습니다.** 출력 형태가 같아야 비교가 됩니다.

**볼 것:**

- 세 모델의 점수 차이가 **얼마나 작은가** — 비슷하게 모이면 "모델이 아니라 **변수가 천장**"이라는 뜻입니다
- 과적합 여부 — 트리 깊이·학습 라운드를 바꿀 때 학습 점수와 검증 점수가 어떻게 벌어지는가
- 하이퍼파라미터 탐색 — 여러 설정을 돌려 성능 폭을 확인
- 학습 시간 — 실험을 몇 번 돌릴 수 있는지를 결정

**선택 기준은 점수만이 아닙니다.** 점수, 학습 속도, 그리고 **해석 가능성**(13단계에서 설명을 뽑아야 함)을 함께 봅니다.

### 12단계 — 확률 보정 (Calibration)

| | |
|---|---|
| **하는 일** | 모델이 말한 확률이 **실제 비율과 맞는지** 재고, 어긋난 만큼 되돌림 |
| **쓰는 변수** | 모델이 출력한 확률 + 정답 `y_class` |

#### 왜 필요한가

우리가 파는 건 **확률 그 자체**입니다. 모델이 "90%"라고 말했는데 실제로 80%만 지켜지면, 다른 점수가 아무리 좋아도 **상품이 거짓말**입니다.

그런데 모델은 "분포 전체가 맞게" 학습됩니다. 그게 **"90%라고 말한 게 정확히 90%"** 를 보장하지는 않습니다. **두 목표가 다릅니다.**

#### "실제로 몇 %였나"를 어떻게 아나 — **모아서 셉니다**

모델이 "이 편은 90% 확률로 18:00까지 도착"이라고 했고, 실제로 17:50에 도착했습니다. 이걸로 "90%가 맞았다"고 할 수 있나요? **못 합니다.** 결과는 도착(1) / 미도착(0) 둘 중 하나고, 90%라는 숫자와 비교할 방법이 없습니다. 비행기는 그날 한 번만 뜨니까요.

**그래서 같은 확률을 받은 편들을 모읍니다.**

```
모델이 "90%" 라고 말한 편을 전부 모은다   →  1,000편
그 편들이 실제로 어떻게 됐는지 센다
            ↓
   800편만 마감 안에 도착  →  실제로는 80% 였다
```

> **일기예보 검증과 똑같습니다.** 기상청이 "비 올 확률 30%"라고 한 날을 100일 모아서 실제로 며칠 비가 왔는지 셉니다. 30일이면 정확한 예보, 50일이면 비를 과소평가하는 예보입니다.

**개별 편은 검증할 수 없지만, 묶으면 검증할 수 있습니다.** 과거 데이터에는 정답이 다 적혀 있으니 이 계산이 가능합니다.

이렇게 **신뢰도 표**를 만듭니다.

```
모델이 말한 확률      모아 보니 실제 비율        판정
──────────────────────────────────────────────────
  50 ~ 60%      →        47%               조금 낙관
  70 ~ 80%      →        71%               괜찮음
  80 ~ 90%      →        79%               조금 낙관
  90 ~ 95%      →        85%               많이 낙관   ←
```
*(위 숫자는 설명용 예시입니다. 실제 값은 측정해서 채웁니다.)*

우리 서비스는 확률을 **8개 구간 경계(0·15·30·60·90·120·180·300분)** 에서 읽으므로, 이 검증을 **경계마다 전부** 합니다.

#### 어떻게 고치나 — **환산표를 만들어 되돌립니다**

> **체온계 비유** —
> ① 이 체온계로 100명을 재면서, 정확한 체온계로도 같이 잽니다
> ② *"이 체온계가 36.0도면 실제는 37.0도"* 라는 **환산표**가 만들어집니다
> ③ 앞으로 36.0도가 나오면 **37.0도라고 읽습니다**
>
> 체온계를 **버리지 않습니다. 읽는 법을 고칩니다.**

같은 일인데, 서비스에서는 두 가지로 보입니다.

**방식 ① 확률을 고친다**

```
모델 출력:  "18:00 까지 도착할 확률 90%"
보정 후:    "18:00 까지 도착할 확률 85%"
```

**방식 ② 시각을 고친다** ← 손님이 보는 화면

```
손님: "90% 로 확실한 시각을 알려줘"

보정 전:  모델이 90% 라고 말하는 지점 = 18:00  →  18:00 제시 (실제로는 85%)
보정 후:  모델이 95% 라고 말하는 지점 = 18:20  →  18:20 제시 (실제로 90%)
```

**"90%를 원하면 모델이 95%라고 하는 지점까지 가야 한다"** — 이게 보정이 하는 일입니다. 보장 시각이 **조금 뒤로 밀립니다.**

> ⚠️ 보정은 성능을 **올리는** 작업이 아니라 **약속을 정직하게 만드는** 작업입니다. 보장 시각이 늦어져서 겉보기엔 상품이 나빠 보이지만, **그게 진짜 숫자입니다.**

#### 어떤 데이터로 환산표를 만드나

| 데이터 | 쓸 수 있나 | 이유 |
|---|:---:|---|
| 학습 데이터 | ❌ | 모델이 이미 외운 데이터라 **원래 잘 맞습니다.** 어긋남이 안 보입니다 |
| 평가 데이터 | ❌ | 최종 평가용으로 아껴둔 데이터. 여기서 만들면 평가가 무의미해집니다 |
| **따로 떼어둔 구간** | ✅ | **모델이 본 적 없고, 정답은 우리가 아는** 데이터 |

그리고 **어느 구간을 쓸지도 실험으로 정합니다.**

```
보정 안 함  /  작년 같은 계절  /  바로 직전 달  /  최근 2주
```

당연히 "가장 최신"이 좋을 것 같지만 확인해야 합니다. **계절마다 지연 수준이 다르다면, "가장 가까운 과거"보다 "계절 구성이 같은 과거"가 더 비슷할 수 있습니다.** 어느 쪽이 나은지는 비교해서 정합니다.

#### 15단계와의 관계

```
12단계 (보정)       따로 떼어둔 데이터에서 어긋남을 재고 → 고친다
                              ↓
15단계 (서비스 평가)  한 번도 안 열어본 평가 데이터에서
                     "80% · 90% · 95% 약속이 실제로 지켜지나" 확인
```

**15단계는 12단계의 시험지입니다.** 보정을 건너뛰면 15단계에서 "90%라 했는데 85%였다"가 나오고, 그건 이 프로젝트의 **핵심 지표가 실패했다**는 뜻입니다.

| **C** 유형을 예측해 합성 | 유형을 먼저 맞히고, 유형별 예측을 가중 평균 | ✅ |

#### 시나리오마다 모델을 따로 학습하지 **않습니다**

여기가 가장 오해하기 쉬운 부분입니다. 유형이 5개니까 모델도 5개 만들 것 같지만, **모델은 하나입니다.**

**입력에 "그날의 유형" 칸을 추가하고, 예측할 때 그 칸만 바꿔서 다시 물어봅니다.**

> 의사에게 물어보는 것과 같습니다.
>
> *"제가 담배를 피우면 어떻게 되나요?"* → 답 A
> *"안 피우면요?"* → 답 B
>
> **의사를 두 명 따로 키우는 게 아닙니다.** 한 명에게 **조건만 바꿔서** 두 번 묻는 겁니다.

##### 학습 (단 한 번)

```
입력 = [ 항공사 · 출발공항 · 도착공항 · 요일 · 월 ·
         예정 출발시 · 예정 도착시 · 거리 · 예정 소요시간 ·
         ★ 출발지 그날 유형 · ★ 도착지 그날 유형 ]

정답 = 10구간 중 어디

           ↓  학습 1회

      모델 B 하나
```

학습할 때는 **그날 실제로 어떤 날이었는지(참값)** 를 유형 칸에 넣습니다. 그러면 모델은
*"출발지가 날씨일이고 저녁 편이면 분포가 이렇게 퍼진다"* 같은 규칙을 배웁니다.

##### 예측 (같은 모델, 유형 칸만 바꿔서 5번)

```
유형 칸에 "평상일" 을 적어 넣고 물어봄     →  평상일 가정의 분포
유형 칸에 "항공사 귀책일" 을 적어 넣고 물어봄 →  그 가정의 분포
유형 칸에 "연결편 붕괴일" 을 적어 넣고 물어봄 →  그 가정의 분포
유형 칸에 "공역 혼잡일" 을 적어 넣고 물어봄  →  그 가정의 분포
유형 칸에 "날씨일" 을 적어 넣고 물어봄      →  그 가정의 분포
```

**나머지 입력(항공사·공항·시각·거리)은 그대로 두고 유형 칸만 고쳐 씁니다.**
그래서 나온 5개의 분포는 *"다른 조건이 모두 같을 때, 그날의 종류만 다르면"* 의 답입니다.

> 시나리오 패널에서는 출발지와 도착지 유형 칸에 **같은 가정**을 넣습니다.
> ("오늘 날씨가 나쁜 날이라면" = 출발지도 날씨일, 도착지도 날씨일)

##### 왜 모델 5개가 아니라 1개인가

| 이유 | 설명 |
|---|---|
| **데이터가 쪼개진다** | 대부분의 날은 평상일입니다. 5개로 나누면 희귀한 유형의 모델은 **배울 데이터가 거의 없습니다.** |
| **같은 걸 5번 다시 배워야 한다** | "저녁 편이 아침 편보다 위험하다"는 **모든 유형에서 똑같이** 성립합니다. 모델 5개는 이 공통 규칙을 각자 따로 배워야 해서 낭비입니다. |
| **비교가 오염된다** | 모델 5개는 각각 다르게 수렴합니다. 그러면 유형별 차이가 **"그날의 종류 차이"인지 "모델이 서로 달라서"인지** 구분할 수 없습니다. 모델이 하나면 차이의 원인은 **입력뿐**입니다. |
| **트리는 알아서 나눈다** | 트리 모델은 "유형" 칸으로 먼저 갈라놓고, 그 아래에서 시각·항공사로 다시 가를 수 있습니다. 즉 **한 모델 안에 유형별 규칙이 이미 들어갑니다.** 모델 5개가 할 수 있는 일을 하나가 포함합니다. |

---

#### 모델 C와 "합성 분포" — 분해가 정보를 만드는지 확인

모델 C는 **"예약 시점 정보로 그날의 유형을 맞힐 수 있나"** 를 예측합니다. 출력은 유형 5개의 확률입니다.

C와 B를 곱해서 더하면, 유형을 모르고도 유형별 예측을 쓸 수 있습니다.

```
합성 분포 = Σ (그날이 유형 s 일 확률) × (유형 s 라면의 분포)
            s
```

> 일기예보 비유 — *"비 올 확률 30%, 맑을 확률 70%"* 이고
> *"비 오면 1시간 늦고, 맑으면 10분 늦는다"* 면
> 평균 예상 지연은 `0.3 × 60분 + 0.7 × 10분`입니다.

**확률의 기본 법칙상 이 합성 분포는 모델 A와 같은 값이 나와야 합니다.** 실제로 같게 나오면,

> **"문제를 원인별로 쪼개서 다시 합치는 것은 정보를 만들지 않는다"**

를 **보여준** 것이 됩니다. "원인별로 나눠서 예측하면 더 정확해질 것"은 많은 사람이 갖는 직관이라, 말로 주장하는 대신 숫자로 확인할 가치가 있습니다.

그리고 B가 A보다 좋은 이유도 분명해집니다 — **쪼갠 덕분이 아니라, 참값을 손에 쥐여줬기 때문**입니다.

#### 왜 쓸 수 없는 B를 만드나 — **천장을 재기 위해서**

B는 **반칙 모델**입니다. 그날이 폭풍이었는지를 미리 알고 예측하니까요. 배포할 수 없습니다.

그런데 B의 점수는 **"그날의 상황을 완벽히 안다면 어디까지 갈 수 있는가"** 를 알려줍니다.

```
A의 점수  =  예약 시점 정보로 도달할 수 있는 현실
B의 점수  =  그날을 알 수 있다면 도달할 천장
    ↓
둘의 격차  =  "실시간 정보의 가격표"
```

이 격차가 하이퍼파라미터를 아무리 튜닝해서 얻는 개선보다 훨씬 크다면, **"우리가 더 노력해도 안 되는 게 아니라, 예약 시점에는 원래 불가능한 영역이 있다"** 는 말을 숫자로 할 수 있습니다.

> ⚠️ **B의 점수를 우리 성능으로 보고하면 안 됩니다.** 반드시 "예약 시점 천장은 A, 그날을 알면 B"로 둘을 같이 적습니다.

#### 그리고 "유형을 맞힐 수 있는가"도 확인합니다

예약 시점 정보로 그날의 유형을 예측해보고, **그냥 가장 흔한 유형으로 찍는 것**과 비교합니다. 못 이긴다면, **시나리오를 "예측"이 아니라 "가정"으로 두는 설계가 데이터로 정당화**됩니다.

### 15단계 — 서비스 평가 ("약속을 지켰나")

| | |
|---|---|
| **하는 일** | **평가 데이터(2026)** 에서 서비스 전체를 시뮬레이션 |
| **쓰는 변수** | 보정된 최종 모델 + 정답 |

> ⚠️ **평가 데이터는 여기서 딱 한 번만 엽니다.** 보고 나서 설계를 바꾸면, 그 데이터는 더 이상 "본 적 없는 미래"가 아닙니다. 설계를 바꿀 필요가 생기면 **검증 데이터에서 예행연습**부터 합니다.

#### 서비스 계산

각 편에 대해 이렇게 계산합니다.

```
여유        = 마감 시각 − 예정 도착 시각        (음수면 바로 탈락)
마감 준수 확률 = 분포에서 "여유 안에 도착할 확률"을 읽음
보장 도착 시각 = 분포에서 "요구 확률이 되는 지점"을 읽음

답 = 마감 준수 확률이 요구 확률 이상인 편 중에서, 출발이 가장 늦은 편
```

**주의할 점 두 가지:**

1. **결항 확률(9번 칸)을 다시 곱하지 않습니다.** 분포는 이미 "도착할 확률"이고, 미도착은 처음부터 빠져 있습니다. 또 곱하면 **두 번 깎는** 셈입니다. 결항 위험은 화면에 **따로** 표시합니다.
2. **보장 시각을 억지로 만들지 않습니다.** 분포가 요구 확률에 도달하지 못하는 편은 **"보장 불가"** 로 그대로 표시합니다.


### 16단계 — 데모 페이지

| | |
|---|---|
| **하는 일** | 예측을 미리 계산해두고, 입력에 따라 답을 보여주는 페이지 |
| **쓰는 변수** | 노선 · 날짜별 분포(보정 완료) + 유형별 분포 |

**화면이 해야 할 것:**

1. **입력** — 노선 · 날짜 · 마감 시각 · **요구 확률(기본 90%)**
2. **메인 답** — 마감을 지키는 **가장 늦은 편** + 보장 도착 시각 + 결항 위험
3. **후보 표** — 그날 모든 편의 출발 시각 · 마감 준수 확률 · 보장 도착 시각 · 통과/탈락
4. **시나리오 패널** — 가정을 바꾸면 **답 자체가 어떻게 바뀌는지**
5. **확률 슬라이더** — 90%→95%로 올리면 **출발이 얼마나 앞당겨지는지** 즉시 반영
6. **한계 각주** — 미국 국내선 여름만 · 가격 없음 · 실시간 없음

**5번이 이 서비스의 가치를 가장 잘 보여주는 화면입니다.**

```
80% 로 만족하면  →  더 늦게 출발할 수 있음
95% 가 필요하면  →  더 일찍 출발해야 함
```

**"확실함의 가격"을 시간으로 보여주는 것** — 이게 다른 어떤 서비스도 안 하는 일입니다.

**분석 원칙 세 가지**

1. **모델이 필요한지 먼저 증명한다.** 표 찾기와 시계 읽기를 정직하게 강하게 만들어 이겨본다.
2. **변수는 상관이 아니라 기여로 판정한다.** 넣어봐서 좋아지지 않으면 버리고, **왜 버렸는지를 기록한다.**
3. **약속한 확률이 실제로 지켜지는지를 최종 지표로 삼는다.** 다른 점수가 좋아도 이게 안 맞으면 상품이 거짓말이다.
