## 2. 사용 범위 — 무엇에 썼고 무엇에 쓰지 않았는가

### 사용한 부분

| 영역 | 어떻게 썼는가 |
|---|---|
| **스크립트 구현** | `src/step*.py` 의 초안 작성. 설계(무엇을 계산할지, 어떤 변수를 쓸지, 어떤 기준으로 판정할지)는 팀이 `docs/PROPOSAL_FLOW.md` 에 먼저 확정하고, AI 에는 그 문서를 근거로 코드를 쓰게 했습니다. |
| **코드 정리** | 반복되는 집계·입출력 코드의 리팩터링, 주석·docstring 작성 |
| **문서 초안** | README 와 보고서의 구조 제안, 한국어 표현 다듬기 |
| **디버깅** | 오류 메시지 해석, pandas/XGBoost API 사용법 확인 |

### 사용하지 않은 부분

| 영역 | 이유 |
|---|---|
| **문제 정의와 서비스 설계** | 무엇을 예측할지(10구간 분포), 누구를 위한 서비스인지, 왜 "가장 늦은 편"인지는 팀의 판단입니다. |
| **변수 설계의 근거** | `absorbed` 를 결측으로 두는 것, `bad_day` 를 상대 분위로 자르는 것, `C` 를 공항 평균과의 차로 만드는 것 — 전부 팀이 먼저 정하고 문서에 적은 뒤 구현했습니다. |
| **채택·기각 판정** | 10단계 게이트의 기준(시드 잡음 2σ)은 숫자를 보기 전에 팀이 정했고, 결과 해석도 팀이 했습니다. |
| **결과 수치** | 모든 숫자는 `src/` 의 스크립트를 실제로 실행해 나온 것이며, AI 가 생성하거나 추정한 수치는 보고서에 하나도 들어가지 않았습니다. |
| **시험(중간·기말)** | 전면 금지 규정에 따라 일절 사용하지 않았습니다. |

## 3. 주요 프롬프트

실제로 사용한 프롬프트의 성격을 대표하는 것들입니다.

1. **파이프라인 구현 요청**
   > "새로운 폴더 만들고 PROPOSAL_FLOW에 맞게 학습을 진행해줘.
   > github 조건에 맞게 저장 및 정리하면서 학습을 처음부터 진행해줘.
   > 프로젝트 요구사항을 반드시 지켜줘."

2. **설계 문서를 근거로 한 구현 지시**
   > "PROPOSAL_FLOW 5단계의 평활 강도 k 를 임의 상수로 두지 말고,
   > 경험적 베이즈로 데이터에서 추정해서 학습 소스 연도에서만 구하도록 써줘."

3. **판정 기준의 사전 고정**
   > "게이트 기준을 결과를 보고 정하면 안 되니까, 같은 설정을 시드만 바꿔
   > 세 번 돌려서 잡음 폭을 먼저 재고 그 2배를 임계값으로 써줘."

4. **검증 코드 요청**
   > "누출이 없다는 걸 글로 주장하지 말고 기계가 돌리는 점검으로 만들어줘.
   > 연도 겹침, 사후 컬럼, train 에서만 적합했는지 전부 확인하도록."

5. **표현 교정**
   > "'추천을 하지 않는다'고 쓰면 모순이야. 포기한 건 순위 매기기이고
   > 남긴 건 마감 경계라는 걸 구분해서 써줘."

## 4. 수정 과정 — AI 결과물을 그대로 쓰지 않은 사례

| AI 초안 | 팀의 수정 | 이유 |
|---|---|---|
| 평활 강도 `k = 10` 같은 상수 사용 | 경험적 베이즈 추정으로 교체 (`k_A=3.99`, `k_C=4.04`) | "임의로 고른 숫자가 없어야 한다"는 프로젝트 원칙 |
| 게이트 판정을 "log loss 가 낮아지면 채택" | 시드 잡음 ±2σ 임계값을 **사전에** 고정 | 0.0003 짜리 변동을 근거로 쓰면 안 됨 |
| `fail_rate` 를 기존 이진 타깃으로 계산 | 10구간 기준 `y_class >= 2`(15분+ 지연 또는 미도착)로 재정의 | 타깃이 바뀌었으므로 파생 지표도 같은 정의를 따라야 함 |
| 원-핫 공항 수를 상위 100개로 고정 | 학습 연도 누적 운항 95% 지점(136개)으로 데이터에서 결정 | 같은 원칙 |
| 서비스 평가에서 전체 노선-날짜 반복 | 시드 고정 표본 25,000개로 축소하고 그 사실을 보고서에 명시 | 실행 시간과 재현성의 균형, 그리고 축소했다는 사실을 숨기지 않기 위해 |
| 그림 라벨이 한글 깨짐 | `src/plotting.py` 로 한글 폰트 설정을 분리 | 보고서에 들어갈 그림이므로 |

## 5. 검증 방법

- 모든 스크립트는 팀이 직접 실행했고, 출력 로그와 `results/` 의 CSV 가 그 증거입니다.
- 주요 주장은 코드로 확인했습니다 — 누출 없음은 `src/verify_leakage.py` (41항목),
  규칙 기반 시나리오의 타당성은 PCA + 군집 교차 검증(`step06`)으로 확인했습니다.
- 보고서의 모든 수치는 `results/` 의 파일에서 그대로 옮긴 것이며,
  각 표에 출처 파일명을 적어 두었습니다.
