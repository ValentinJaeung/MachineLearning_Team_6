## 1. 문제 정의와 동기

### 1-1. 표에 적힌 도착 시각은 약속이 아니라 계획이다

항공권에는 이렇게 적혀 있습니다.

```
17:00 출발  →  19:00 도착
```

손님은 이 "19:00"을 약속으로 읽고 일정을 짭니다. *"20:00에 회의가 있으니 1시간
여유네."* 그런데 학습 데이터(2022–24년 미국 국내선 여름 540만 편)에서 **예정 시각
이내에 도착한 편은 57.3%** 뿐입니다. 19:00은 절반을 조금 넘는 확률로만 맞는
숫자이고, 그 위에 세운 계획도 그만큼만 맞습니다.

전체 분포로 보면 **90%가 지켜지는 지점은 예정 도착 +73분**, 95%는 **+154분**입니다
(`results/step08_class_distribution.csv`). 손님이 믿고 있는 숫자와 실제로 믿을 수
있는 숫자 사이에 한 시간 이상이 비어 있습니다.

### 1-2. 우리가 만드는 것

| | |
|---|---|
| **사용자** | 도착한 뒤에 **미룰 수 없는 약속**이 있는 사람 (회의·결혼식·공연·별도 발권 환승·마중) |
| **쓰는 시점** | **예약하기 직전** — 편을 바꿀 수도, 약속 시각을 바꿀 수도 있는 유일한 순간 |
| **입력** | 노선 · 날짜 · **몇 시까지 도착해야 하는지** · **몇 %로 확실해야 하는지**(기본 90%) |
| **출력** | 그 마감을 지키는 **가장 늦은 편** + 보장 도착 시각 + 결항 위험 + 후보 편 목록 |

### 1-3. 왜 "가장 늦은 편"인가

"안전하려면 첫 비행기를 타라"는 누구나 압니다. 어려운 것은 **경계를 찾는 일**입니다.

```
너무 늦은 편  → 약속을 놓침
너무 이른 편  → 하루를 통째로 버림
        ↑
   우리가 찾는 건 이 사이의 마지막 안전한 편
```

그래서 이 프로젝트가 포기한 것과 남긴 것을 분명히 구분합니다.

- **포기한 것**: "어느 편이 더 안전한가"라는 **순위 매기기**. 이건 상식이 이미 답을 줍니다.
- **남긴 것**: "마감을 지키면서 가장 늦게 떠날 수 있는 편"이라는 **경계 계산**.
  사람이 머리로 할 수 없는 건 이것뿐입니다.

### 1-4. 그래서 "하나의 숫자"가 아니라 "분포"를 예측한다

흔한 접근은 *"이 비행기 지연될까요? 예/아니오"* 입니다. 이게 안 되는 이유가 있습니다.
**"늦었다"의 기준이 사람마다 다릅니다.**

```
A씨: 18:00까지 가야 함  →  18:10 도착은 실패
B씨: 21:00까지 가야 함  →  18:10 도착은 대성공
```

같은 비행기, 같은 결과인데 한 사람에게는 실패이고 다른 사람에게는 성공입니다. 고정
임계값 하나로는 두 사람에게 같은 답밖에 줄 수 없습니다.

그래서 **10개 구간의 확률을 전부** 내놓습니다 (≤0 / 0–15 / 15–30 / 30–60 / 60–90 /
90–120 / 120–180 / 180–300 / 300분+ / 미도착). 마감 시각과 요구 확률은 **손님에게
넘기고**, 모델은 분포만 만듭니다. 한 번 학습한 모델이 A씨와 B씨에게 각각 다른 답을
줄 수 있습니다.

```
누적합을 앞에서부터 더하면   →  "몇 분 안에 도착할 확률"
거꾸로 읽으면              →  "90%가 되는 지점" = 90% 보장 도착 시각
10번째 칸                 →  결항·회항 실패 위험
```

## 2. 선행연구와 포지셔닝

> 아래는 공개 서비스의 기능 수준에서 비교한 것입니다. 인용 링크는 팀이 제출본에
> 추가합니다.

| | 무엇을 주는가 | 우리와 다른 점 |
|---|---|---|
| **항공사 / 예약 사이트** | 예정 도착 시각 하나 | 그 시각이 지켜질 확률을 말하지 않음 |
| **Google Flights 지연 표시** | 특정 편에 대한 지연 가능성 안내 | **편 단위 라벨**이지, "내 마감"을 입력받지 않음 |
| **FlightAware · FlightStats 등** | 과거 정시율 통계, 실시간 추적 | **이미 예약한 뒤**에 쓰는 도구. 예약 전 의사결정용이 아님 |
| **BTS 공개 통계** | 노선·항공사별 정시율 집계 | 집계값이지 개별 편의 분포가 아님 |

**비어 있는 자리.** 기존 서비스는 모두 *"이 편이 늦을 것 같은가"* 에 답합니다. 아무도
*"내 마감이 20:00이고 90%로 확실해야 하는데, 몇 시 편까지 괜찮은가"* 에 답하지
않습니다. 마감과 요구 확률을 **사용자 입력으로 받는** 것이 이 프로젝트의 포지션이고,
그것이 가능하려면 예측 대상이 하나의 숫자가 아니라 **분포**여야 합니다.

또한 기존 서비스는 대부분 **실시간 정보**(당일 기상, 지연 전파)를 씁니다. 우리는 쓰지
않습니다 — 예약 시점에는 그 정보가 **존재하지 않기** 때문입니다. 대신 그 정보가
얼마나 가치 있는지를 숫자로 재서 보고합니다(§5, 모델 B).

## 4. 방법

### 4-1. 전체 흐름

```
[재료]   1 수집 → 2 정제·키·라벨 → 3 연결편 ┐
                                       ├→ 5 키별 작년 성적표
                      → 4 공항-날짜 상태 ┘
                      → 6 그날의 유형
[데이터셋] 7 결합·연도 분할 → 8 EDA(설정값 확정) → 9 전처리 두 벌
[모델링]  10 변수 선택 → 11 모델 3종 → 12 확률 보정 → 13 해석 → 14 시나리오
[서비스]  15 서비스 평가(test 2026) → 16 데모 데이터
```

각 단계는 `src/stepNN_*.py` 하나에 대응하고, `python run_all.py` 로 순서대로
재현됩니다.

### 4-2. 누출을 막기 위한 변수 분류

`src/config.py` 한 파일에 네 그룹을 정의하고, `src/verify_leakage.py` 가 그 정의를
그대로 점검합니다.

| 그룹 | 성격 | 모델 입력 |
|---|---|:---:|
| 🟢 A-1 (9) | 예약 화면에서 보이는 값 | ✅ 후보 |
| 🟢 A-2 (3) | 식별자 — 날짜·편명·기체번호 | ❌ 조인·분할 전용 |
| 🔴 B (5) | 결과 | ❌ 정답 생성 전용 |
| 🟡 C (13) | 사후 정보 | ❌ "그날의 상태" 생성 전용 |

**`Tail_Number` 를 쓰면서도 누출이 아닌 이유.** 예약 시점에는 어느 기체가 들어올지
알 수 없습니다. 그래서 이 변수는 **작년 데이터에서만**, 그것도 "그 기체의 그날 운항
사슬"을 복원하는 데만 씁니다. 복원 결과를 편명·노선 키로 집계해 올해 편에 붙이므로,
올해 편에 대해 묻는 것은 "작년에 이 편명·이 노선이 어땠나"뿐입니다.

### 4-3. 설계 결정과 그 근거

임의로 고른 숫자가 없다는 것이 이 프로젝트의 설계 원칙입니다.

| 결정 | 근거 (측정값) | 어디서 |
|---|---|---|
| **이상치를 제거하지 않음** | 꼬리가 곧 상품. 90% 보장 시각은 분포 꼬리에서 읽힘 | §1-1 |
| **회항 후 도착 = 지연 구간** | 손님에게는 "다른 사건"이 아니라 아주 늦은 도착 | step02 |
| **`absorbed` 를 결측으로** | 앞 편이 안 늦었으면 삼킬 지연이 없음. 0으로 채우면 "시험 안 본 사람"을 "틀린 사람"으로 집계 | step03 |
| **나쁜 날 = 공항·연도 상대 분위** | p90 임계값이 공항·연도별로 **−8.5분 ~ 199.0분** (중앙값 35.2분). 절대 기준은 "그날이 나빴나"가 아니라 "이 공항이 붐비나"를 잼 | step04·08 |
| **평활 강도 k = 경험적 베이즈** | 내부분산/진짜 키간분산으로 추정 → **k_A 3.99 · k_C 4.04**. 학습 소스 연도에서만 추정 | step05 |
| **성적표 조인 = 계층 축소** | `flight_key` 만으로는 train의 **25.2%** 만 매칭. 편명은 해마다 재배정되는 번호표 | step07·08 |
| **원-핫 공항 = 상위 136개** | 학습 연도 누적 운항 95% 지점. 나머지 231개는 운항의 4.9% | step08 |
| **시각은 선형 쪽에서만 원-핫** | 05시 정시 77.7% → 20시 43.5% → 23시 반등. 숫자 한 칸으로는 직선 하나뿐 | step08·09 |
| **시나리오 = 공항-날짜 라벨** | 편에 붙이면 결과로 결과를 설명. BTS는 늦은 편에만 원인을 기록 | step06 |
| **시나리오는 예측이 아니라 가정** | 예약 시점 예측 정확도가 최빈값 찍기를 못 이김 | step14 |
| **보정 필수** | 상품이 확률 그 자체. 90%라 말하고 85%면 거짓말 | step12 |

### 4-4. 핵심 파생 변수 — 왜 그렇게 만들었나

**③ 연결편 (`day_seq`, `turnaround_min`, `prev_delayed`, `absorbed`)**
같은 기체가 하루에 여러 번 뜹니다. 앞 비행이 늦게 들어오면 다음 편은 출발 전부터
불리합니다. 전체 지연 분(分)의 **40.7%가 "연결편 지연"** 이라는 사실이 이 변수를
만든 근거입니다(`figures/step08_cause_mix.png`). 네 조건(동일 기체·동일 날짜·공항
연결·앞 편 비결항)을 모두 만족할 때만 연결로 인정했고, 연결률은 73~74%입니다.

**⑤ `C_bad_day_rel_fail` — 가장 공들인 변수**
나쁜 날의 "그냥 실패율"을 쓰면 "나쁜 날이 많은 공항에 있나"를 재게 되고, 그건 공항
이름이 이미 아는 정보입니다. 그래서 **빼서** 만듭니다.

```
C = (그 편이 실패했나) − (그날 그 공항 전체의 실패율)
```

같은 날 같은 공항의 다른 편이 기준선이 되므로 날씨·관제 같은 공통 요인이 상쇄되고
그 편 고유의 튼튼함만 남습니다.

**평활이 필요한 이유가 데이터에 있습니다.** `flight_key` 당 나쁜 날 관측 횟수의
중앙값이 **1회**입니다(`figures/step08_key_match.png`). 동전 한 번 던진 결과로
"완벽한 편 / 최악의 편"이 정해지면 안 됩니다.

### 4-5. 판정 기준을 숫자 보기 전에 고정했다

변수를 넣을지 말지는 **상관이 아니라 기여**로 판정합니다. 상관이 있어도 다른 변수가
같은 정보를 담고 있으면 넣어도 아무것도 바뀌지 않고, 잡음만 늘어 나빠질 수도
있습니다.

그 "바뀌었다"의 기준을 사후에 정하면 아무 숫자나 근거가 됩니다. 그래서 **같은 설정을
시드만 바꿔 세 번 돌려** 실행 간 잡음을 먼저 재고(sd 0.000133), 그 **2배인
0.000265** 를 임계값으로 **미리** 고정했습니다(`results/step10_noise.csv`).
