### 4.1 전체 파이프라인

### 4.2 데이터 전처리 방법
**📊 결과 있음**

**기존 변수 9개**

- **범주형 5개**(항공사·출발공항·도착공항·요일·월): 공항은 수가 많아 EDA 에서
  정한 **129개만 남기고 나머지 10개를 '기타'로 묶었다.** 판단은 학습 연도만 보고 했다
- **시각**: `1435` 같은 원본 표기를 쓰지 않고 **시(hour) 단위로 바꿨다.**
  이유 — 1359와 1400은 1분 차이인데 정수로는 41 차이다
- **그 시각을 모델마다 다른 형태로 넣었다** (3.1-③ 의 꺾인 모양 때문이다)

  | | 넣은 형태 | 왜 |
  |---|---|---|
  | 로지스틱·MLP | **0·1 열 24개**로 펼침 | 숫자 하나로 넣으면 계수도 하나뿐이라 **직선밖에 안 된다.** 24개 시각이 각자 계수를 가져야 꺾인 모양이 표현된다 |
  | XGBoost | **숫자 0~23 그대로** | 트리는 `시각<10?` → `시각<6?` 하고 **여러 번 쪼개므로** 숫자 하나로도 꺾인 모양을 만든다 |

  **다항 특성(시각²·시각³)을 쓰지 않은 이유:** 시각은 값이 24개뿐인 **이산 변수**라
  0·1 열 24개가 가능한 가장 유연한 표현이고, 다항식은 그 24개 점을 매끄러운 곡선으로
  근사하는 것이다. 더 중요한 것은 **시각이 순환한다**는 점이다 — 23시의 반등은 사실
  새벽의 높은 정시율이 시작되는 지점인데, 다항식은 `0~23` 범위의 숫자로 보므로
  **23과 0을 가장 먼 값으로 취급한다.** 차수를 올려도 이 연결은 만들어지지 않는다.
  펼치는 비용도 작다 — 349열 중 48열(출발·도착 시각)이고, 학습 474만 편이므로
  시각 열 하나마다 평균 20만 편이 받친다
- **수치형 결측**: **학습 구간 중앙값**으로 대체. 그 값을 검증·평가에 그대로 적용
- **이상치**: 따로 자르지 않았다. 지연의 긴 꼬리가 바로 우리가 맞히려는 대상이다
- **제외한 행**: 예약 정보(예정 시각·거리·비행시간)가 비어 있는 행 **3편**.
  지연 값이 없어 결과를 알 수 없는 행은 **0편**이었다 — 결항·회항은 미도착으로
  들어가므로 버려지지 않는다

**파생 변수 2개**

- **도착지 혼잡**(`dest_arr_load`): 같은 날짜·같은 시각에 그 도착지로 들어오도록
  예정된 편 수. **올해 시간표만으로 계산되므로 예약 시점에 알 수 있다.**
  평균 22.0~24.0편, 최대 107편
- **공휴일까지 일수**(`days_to_nearest_holiday`): 가장 가까운 공휴일까지의 부호 있는
  일수(음수 = 공휴일 전). **±21일에서 자른다** — 더 먼 값은 의미가 없다.
  대상 공휴일은 메모리얼데이·준틴스·독립기념일·노동절 (`step02_holidays.csv`)

**유형 변수 2개** — 아래가 실제로 구현한 규칙이다.

- 라벨을 **(공항, 날짜)** 에 붙인다. 항공편 하나에 붙이지 않는 이유: 원인 컬럼은
  **이미 늦은 편에만 기록**되므로 정시 편과 비교할 기준이 없다
- **그날이 나쁜 날인지 판정**: 그 공항-날짜의 실패율이 **그 공항의 평소 수준**보다
  높은가. '실패'는 **15분 초과 지연 또는 미도착**. '평소 수준'은 그 공항의
  날짜별 실패율 평균을 **연도 안에서** 계산한 값
- **나쁜 날이면 원인을 고른다**: 원인별 지연 분(分)의 비중에서 가장 튀는 것.
  **그 공항 안에서 표준화한 뒤** 비교한다 — 공항마다 기본 성향이 다르다
  (산악 지역은 원래 날씨 분이 많다). 원인은 4개:
  `CarrierDelay` · `LateAircraftDelay` · `NASDelay` · `WeatherDelay` (Security 제외)
- **나쁜 날이 아니면 '정상일'**
- **자기 편은 집계에서 뺀다** (leave-one-out) — 작은 공항에서는 그 편이 자기 답을
  읽게 되므로. **이것이 누출 방지 처리다**
- **그 공항-날짜에 20편 미만이면 라벨하지 않는다** — 몇 편으로 그날을 규정할 수 없다.
  라벨 못 한 행은 버린다 (**12.2%**)
- **출발지와 도착지에 각각 붙인다 → 그래서 2열**

> **이 2열은 예약 시점에 알 수 없다.** 실현된 지연과 원인 분으로 사후에 붙인
> 라벨이기 때문이다. 그래서 손님에게 고르라고 하지 않고 **25칸을 전부 보여준다.**
> (4.4 와 연결)

### 4.3 3개의 모델 선택한 이유
**✍️ 사람이 씀** — "어떤 모델인지"와 "왜"는 직접 쓰고, 아래 사실만 가져다 쓰면 된다.

| 모델 | 이 데이터에서 맡은 역할 |
|---|---|
| **로지스틱 회귀** | 기준선. 변수 사이 상호작용을 **못 쓰는** 모델이 어디까지 가는지 보여준다 |
| **MLP** | **변수들의 조합 효과**를 표현할 수 있다 — "날씨일이면서 동시에 저녁 시간대" 처럼, 각 변수의 효과를 더하는 것으로는 안 나오는 것 |
| **XGBoost** | 범주 변수를 **펼치지 않고** 그대로 쓰고, 변수 조합을 자동으로 찾는다 |

실제 결과(6.1)로 보면 **MLP·XGBoost 가 거의 같고 로지스틱만 0.0227 뒤처졌다.**
해석은 7.2 에서 쓴다.

### 4.4 우리 서비스에 대한 설명
**📊 결과 있음**

- 모델이 **10구간 확률**을 낸다
- 경계 안쪽 8칸을 **누적**한다 → "그 시간 안에 도착할 확률"
  (300분+ 와 미도착은 어느 경계 안에도 안 들어가므로 누적에서 뺀다. 그래서 곡선
  상한이 1.0 보다 낮고, 모자란 만큼이 **"그 시간 안에 못 올 확률"** 이다)
- 누적이 **0.80 에 처음 닿는 경계**를 읽는다 → 이것이 **보장 지연**
- 끝까지 0.80 에 닿지 못하면 **'보장 불가'** 로 표시한다 (약속을 팔지 않는다)
- 손님이 **항공편 하나를 고르면**, 그 항공편의 **25칸**을 전부 보여준다

**실제 한 편 예시** — OO항공 ORD→ALB, 2026-06-16 14시 출발
(80% 보장 지연, 분. 예정 도착 시각 기준)

| 출발지↓ / 도착지→ | 정상일 | 항공사귀책일 | 연결편붕괴일 | 공역혼잡일 | 날씨일 |

| **정상일** | 15 | 15 | 15 | 15 | 15 |
| **항공사귀책일** | 30 | 30 | 30 | 60 | 60 |

**같은 항공편인데 15분부터 180분까지 12배로 벌어진다.** 유형 2열을 입력에 넣은

### 5.2 모델별 학습·튜닝 방법
**📊 결과 있음** — 실제로 돌린 설정이 전부 아래에 있다. **총 10회 적합.**

**로지스틱 회귀**

| | |
|---|---|
| 입력 형태 | 범주 변수를 0·1 열로 펼침 → **349열** (희소 행렬) |
| 탐색한 것 | **규제 강도 C 3개 값**: 0.1 · 1.0 · 10.0 |
| 과적합 대책 | **L2 규제** |
| 최적화 | lbfgs, 최대 400 반복 |
| 실제 결과 | 세 설정 **모두 수렴**(144~146 반복). 검증 log loss 차이가 **0.00004** 뿐 |

**MLP**

| | |
|---|---|
| 입력 형태 | 범주 변수를 0·1 열로 펼침 → **349열** |
| 탐색한 것 | **구조 2개**: (256, 64) / (512, 128, 32) · **학습률 2개**: 3e-4 / 1e-3 |
| 과적합 대책 | **드롭아웃 0.2** + **검증 log loss 가 가장 낮은 에폭 선택** |
| 학습 조건 | 배치 8,192 · 최대 8 에폭 |
| 실제 결과 | 세 설정 **모두 7에폭에서 검증이 최저**였고 8에폭에서 다시 올라갔다 |

**XGBoost**

| | |
|---|---|
| 입력 형태 | 범주 변수를 **그대로** (native categorical) → **13열** |
| 탐색한 것 | **max_depth 3개**: 3 · 6 · 10 · **learning_rate 2개**: 0.05 · 0.10 |
| 과적합 대책 | **조기 종료**(40라운드 인내) · subsample 0.8 · colsample 0.8 · min_child_weight 50 |
| 학습 조건 | 최대 400 라운드 |
| 실제 결과 | depth 10 은 204라운드, eta 0.10 은 283라운드에서 조기 종료. **기준 설정(depth 6)과 depth 3 은 400라운드를 다 썼다** (→ 「측정된 한계」 ①) |

**공동**

- **결측은 학습 구간 중앙값으로, 표준화는 학습 구간 평균·표준편차로.**
  그 값을 검증·평가에 **그대로 적용**했다
- **클래스 불균형 처리를 하지 않았다.** 가중치나 리샘플링을 쓰면 모델이 내는
  확률이 실제 비율에서 벗어난다. **우리는 확률 자체를 팔기 때문에 건드리지 않는다**
- **탐색 방식: 한 번에 하나씩 바꾸기(one-at-a-time).** 격자 전체를 돌릴 필요 없음
- **시드 42 고정** (python random · numpy · torch, 그리고 결정론적 연산 강제)

→ `final/results/step06_search.csv`

### 5.3 평가 지표 정의 (모델 비교용)
**📊 결과 있음**

- **주 지표: Multiclass Log Loss** — 10구간 확률분포 **전체**가 실제와 맞는지 본다
- **검증 구간에서 가장 낮은 모델 하나를 고른다. 끝이다.**
- 지표를 하나로 둔 이유: 세 계열 모두 **이 값을 낮추도록 학습된다**
  (lbfgs 의 수렴 조건, XGBoost 의 조기 종료, MLP 의 에폭 선택이 전부 log loss 를 읽는다).
  적합 절차가 최적화하지 않는 다른 양으로 고르면 공정하지 않다
- 선택 규칙은 **숫자를 보기 전에** 정해 뒀다 (`final/results/step07_decision.json`)

### 5.4 확률 보정 방법
**📊 결과 있음**

- **무엇을 고치는가**: 모델이 "80%"라고 한 것과 **실제로 그 안에 도착한 비율**의 차이
- **어떻게**: 경계 8개마다, 검증 구간에서 "모델이 말한 누적확률 → 실제 비율" 대응을
  **isotonic regression**(단조증가 함수)으로 학습. 사이킷런 한 줄
- **단조증가로 제한하는 이유**: "모델이 더 높은 확률을 준 편이 실제로도 더 자주 그
  안에 도착한다"는 **순서만은 지켜야** 한다
- **어디서 적합하고 어디에 적용하는가**: **검증 2025 에서 적합 → 평가 2026 에 적용.**
  평가에서 적합하면 정답을 보고 확률을 고친 것이 되어 누출이다
- **보정 후 처리**: 경계별로 따로 고치면 누적이 거꾸로 가는 칸이 생길 수 있으므로
  **단조증가하도록 정렬**한다 (`np.maximum.accumulate`)
- **성격**: 보정은 **성능 개선이 아니라 정직성 작업**이고, 그 대가로 보장 시각은
  뒤로 밀린다 (6.2 에서 실제로 2.6분 밀렸다)

### 5.5 서비스 검증 방법 정의
**📊 결과 있음**

- 평가 구간 전체를 **한 번** 예측한다. 각 편에 **그 편의 실제 조합**을 입력으로 넣는다
- 0.80 에 닿지 못하는 편은 **'보장 불가'** 로 분류하고 **분모에서 뺀다**
- 실제 지연이 보장 지연 이내면 **'지킴'**, 결항·미도착은 **'못 지킴'**
- **전체**: 모든 편을 묶어서 이행률을 센다
- **조합별**: **실제 조합**으로 25개 그룹으로 나눠 칸마다 이행률을 센다
- 편수가 1,000편 미만인 칸은 **'판단 불가'** 로 표시한다
  → 실제로는 **판단 불가 칸이 0개**였다 (가장 얇은 칸도 14,429편)

**각 편에 실제 조합을 넣는 이유**: 손님에게 25칸을 모두 보여주는 서비스이므로
표 안에는 **항상 맞는 칸이 들어 있다.** 검증은 "**그 맞는 칸이 약속을 지키는가**"를
확인하는 것이다.

### 5.6 서비스 평가 지표 정의
**📊 결과 있음** — **네 지표는 반드시 같이 읽어야 한다.**

| 지표 | 정의 | 목표 |
|---|---|---|
| **약속 이행률** | 보장 지연 이내에 도착한 편의 비율 | 0.80 이상 |
| **이행률 오차** | 이행률 − 0.80 (양수면 안전, 음수면 과신) | ≥ 0 |
| **평균 보장 지연** | 보장 시각이 얼마나 뒤로 밀렸는지 | 작을수록 좋음 |
| **보장 불가 비율** | 0.80 에 닿지 못한 편의 비율 | 작을수록 좋음 |

**이행률만 보면 보장 시각을 뒤로 밀어 얼마든지 올릴 수 있다.** "모든 편이 10시간
안에 온다"고 하면 이행률은 100% 가 된다. 그래서 평균 보장 지연과 보장 불가
비율을 항상 같이 낸다.

## 측정된 한계 (7.3 재료)

**① MLP 와 XGBoost 의 차이는 아주 작다 — 예산을 늘려도 뒤집히지 않았다.**

step06 에서 XGBoost **두 설정(기준 depth6 · depth 3)이 400라운드 상한을 다 쓰고
끝났다.** 조기 종료(40라운드 인내)가 걸리지 않았다는 뜻이고, 그래서 "더 돌리면 좋아질 여지가 남아
있었다" 는 말을 해야 했다. 그 여지를 **측정했다** — 상한만 3000으로 올려
**조기 종료가 스스로 걸릴 때까지** 다시 돌렸다(`step06b`). 설정·시드·인내(40)는
전부 그대로 두고 **바꾼 것은 라운드 상한 하나뿐이다.**

| 설정 | 400라운드로 끊었을 때 | 끝까지 돌렸을 때 | 멈춘 지점 |
|---|---|---|---|
| 기준 depth6 eta0.05 | 1.351794 | **1.351507** | 최적 580 / 돌린 620 라운드 |
| depth 3 | 1.360516 | 1.354709 | 최적 2413 / 돌린 2453 라운드 |

**둘 다 스스로 멈췄다.** 상한이 더는 아무 역할도 하지 않았다는 뜻이다. 그런데도
MLP(**1.351091**)를 넘지 못했다 — 차이가 0.000703 에서 **0.000416** 으로
줄어든 것이 전부다. 그래서 **채택은 MLP 그대로**이고, 보정(6.2)·평가(6.3)도
다시 돌리지 않았다.

**읽는 법:** "MLP 가 더 좋은 알고리즘이다" 가 아니다. **두 계열이 사실상 같은
수준**이고, 우리 지표에서는 MLP 가 소수점 넷째 자리에서 앞선다. 판단은 **검증
2025 로만** 했다 — 이 비교에 평가 구간(2026)은 쓰지 않았다.

**② 보정은 평가 구간에서 완전히 맞지 않는다.**
검증 2025 에서 CDF 보정오차가 0.000000 까지 떨어지는데 평가 2026 에서는
0.015704 → 0.011507 로만 줄어든다. **적합한 해와 적용하는 해가 다르기 때문이다.**
보정은 눈금을 완전히 고치는 장치가 아니라 **해가 바뀌어도 남는 치우침을 줄이는 장치**다.

**③ 모델은 낙관적인 쪽으로 치우쳐 있다.**
보정 전 평균 확률이 경계 8개 중 7개에서 실제 비율보다 높았다(최대 +0.0092).
즉 **"제 시간에 올 것"이라고 과하게 말한다.** 보정이 이걸 되돌리면서 평균 보장
지연이 38.9분 → 41.5분으로 뒤로 밀렸다. 이게 정직함의 대가다.

**④ 날씨일 칸 두 개는 약속을 지키지 못했다.**
날씨일×날씨일 0.7496, 날씨일×공역혼잡일 0.7843. **날씨가 나쁜 날의 꼬리가 구간
8개로는 잡히지 않는다**(보장 불가도 10.6% · 12.4% 로 25칸 중 가장 높다).
**이 한계는 고치지 않고 그대로 보고한다.** 두 칸을 "보장 불가"로 바꿔서 다시 재면
평가 구간의 결과를 보고 서비스를 손본 것이 되어, **연도로 분할한 이유가 사라진다.**

**⑤ 유형 2열은 예약 시점에 알 수 없다.**
실현된 지연과 원인 분으로 사후에 붙인 라벨이다. 그래서 25칸을 전부 보여주는
설계를 택했다 — **손님이 틀린 칸을 고를 가능성 자체를 없앴다.** 대신 손님은
"어느 칸이 내 경우인지"를 스스로 모른다.

**⑥ 유형 라벨 단계에서 12.2% 의 행을 버렸다.**
그 공항-날짜에 20편 미만이어서 그날을 규정할 수 없는 경우다. **작은 공항이
구조적으로 더 많이 빠진다.**

**⑦ 여름(6·7·8월)만 썼다.** 겨울 폭설·결빙 지연은 이 모델이 본 적이 없다.

**⑧ 탐색이 작다.** 계열별 3~4개 설정, 한 번에 하나씩 바꾸기, 총 10회 적합.
교차검증은 하지 않았다(연도 분할이므로 — 이유는 문서 맨 아래 「참고」 에 있다).
학부 프로젝트 규모에서 정한 범위다.

**⑨ 로지스틱의 비선형 표현은 시각에서만 해 줬다.**
로지스틱 회귀는 log-odds 를 입력의 **선형 결합**으로 두는 모델이라, 튜닝(규제 강도 C)은
계수의 크기만 바꿀 뿐 함수의 모양은 바꾸지 못한다 — 실제로 C 를 100배 바꿔도 검증이
**0.00004** 밖에 움직이지 않았다(6.1). 이 한계는 튜닝이 아니라 **입력을 바꿔서**
넘을 수 있다. 우리는 그것을 **시각 하나에만** 했다(0·1 열 24개, 4.2). 나머지는 그대로다.
- 수치 4개(`Distance` · `CRSElapsedTime` · `dest_arr_load` · `days_to_nearest_holiday`)는
  **표준화한 열 하나씩**으로 들어가므로, 각 변수의 효과가 **한 방향 직선**으로만 표현된다
- **교호작용 항을 하나도 넣지 않았다.** "출발지 날씨일 **이면서** 도착지 공역혼잡일" 같은
  조합 효과는 로지스틱이 원리적으로 표현하지 못한다
넣지 않은 이유는 로지스틱의 역할이 **상호작용을 못 쓰는 모델이 어디까지 가는지 보는
기준선**(4.3)이기 때문이고, 넣을 수 있는 조합이 너무 많아서 이기도 하다(공항 130 × 시각 24
하나만으로 3,120열). 조합을 스스로 찾는 일은 MLP·XGBoost 가 맡았다. 그래서 로지스틱이
0.0227 뒤처진 것(6.1)은 **알고리즘의 한계와 우리가 입력을 설계하지 않은 몫이 섞인 값**이다.
변환을 넣었을 때 이 차이가 얼마나 줄어드는지는 **재지 않았다.**

## 참고 — 교차검증(K-Fold)을 왜 쓰지 않았나

팀원이 물어볼 수 있는 내용이라 적어 둔다. **쓰지 않은 것이 맞다.**

**무작위 폴드(KFold·StratifiedKFold)는 이 데이터에서 쓸 수 없다.**
행이 서로 독립이 아니다 — 같은 `(공항, 날짜)` 에 수백 편이 들어 있고 그 수백
편이 **같은 날씨·같은 유형 라벨을 공유한다.** 무작위로 나누면 같은 날의 다른
편이 학습과 검증에 동시에 들어가서, 모델이 **그날 날씨를 이미 본 상태로**
점수를 받는다. 파생 변수 두 개도 날짜 기준 집계라 같은 경로로 새어 나간다.
(5.1 의 "왜 섞지 않는지" 와 같은 이유다)

**시간 순서를 지키는 교차검증은 가능했다.** `2022→2023`, `2022·23→2024`,
`2022·23·24→2025` 처럼 겹을 쌓는 방식이다. 우리는 그중 **마지막 한 겹만**
썼다 — 즉 단일 홀드아웃이다.

**한 겹으로 충분한지 확인했다.** 교차검증의 목적은 성능 추정치의 흔들림을
줄이는 것인데, 검증 편수가 **1,628,703 편**이라 그 흔들림이 애초에 작다.
저장된 검증 예측(`data/model/val_probs_*.npy`)으로 계산한 값이다.

| | 검증 log loss | 평균의 표준오차 |
|---|---|---|
| MLP | 1.351091 | 0.000914 |
| XGBoost(길게) | 1.351507 | 0.000913 |

같은 항공편끼리 짝지어 뺀 차이(두 모델이 같은 편을 보므로 이쪽이 맞는 비교):

| 비교 | 차이 | 표준오차 | t |
|---|---|---|---|
| XGBoost(400라운드) − MLP | +0.000703 | 0.000133 | +5.29 |
| XGBoost(끝까지) − MLP | +0.000416 | 0.000135 | +3.09 |

**MLP 가 앞선 것은 우연이 아니다** — 차이가 그 표준오차의 3배다. 폴드를 더
나눠도 순위는 뒤집히지 않는다. 다만 **"MLP 가 의미 있게 더 좋다"는 뜻은
아니다.** 통계적으로 구분될 뿐 크기는 넷째 자리이고, 서비스 지표(약속 이행률
83.1%)에서는 보이지 않는 차이다.

**한 줄로:** 교차검증을 빠뜨린 것이 아니라, 무작위 폴드는 누출 때문에 틀린
도구였고, 162만 편 단일 홀드아웃이 교차검증이 주는 것(안정된 추정치)을 이미
주고 있었다.
