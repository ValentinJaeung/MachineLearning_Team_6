# 비행기 도착 시각 예측 — 기계학습기초(AAI332) 2026-2학기 6조

손님이 항공편을 고르면, **출발지 유형 × 도착지 유형 25개 조합마다**
**80% 확률로 도착하는 시각**을 알려준다.

```
입력  13열
      ├─ 9열  BTS 원자료에서 그대로          (예약 시점에 아는 것)
      ├─ 2열  공개 시간표에서 계산한 파생     (예약 시점에 아는 것)
      └─ 2열  그날의 유형 — 출발지 / 도착지   (예약 시점에 알 수 없는 것)
출력  10구간 확률분포 → 누적 → 0.80에 처음 닿는 경계 = 80% 보장 지연
```

---

## 실행

```powershell
pip install -r requirements.txt
```

```powershell
python src/step01_label.py
```

원자료는 **이 프로젝트에서 다시 받지 않는다.** 이미 내려받아 둔
`../data/raw/{year}_{mm}.parquet` 을 읽는다. 다른 곳에 있으면
환경변수 `FINAL_RAW_DIR` 로 경로를 지정한다.

모든 난수는 `src/config.py` 의 `SEED = 42` 하나에서 나오고, 각 스크립트는
맨 앞에서 `config.set_seeds()` 를 부른다.

하는지**가 적혀 있다. 그것이 이 프로젝트의 설계 문서다.

`step06b`·`step06c` 는 `run_all.py` 에 넣지 않았다. 본 파이프라인이 아니라
**한계 하나를 확인하려고 따로 돌린 단계**이고, 결과는 「알려진 한계」 1번에 있다.
step06 의 산출물을 덮어쓰지 않는다.

`data/` 는 중간 산출물이라 저장소에 넣지 않는다. `results/` 와 `figures/` 가
보고서에 들어가는 전부다.

## 확정된 설계 결정

### 데이터

| | |
|---|---|
| 출처 | 미국 교통통계국(BTS) On-Time Performance — 퍼블릭 도메인 |
| 범위 | 2022–2026년 **6·7·8월**, 미국 국내선 전체, 항공사 제한 없음 |
| 분할 | 학습 2022·2023·2024 / 검증 2025 / 테스트 2026 |

여름만 쓰는 이유는 계절마다 지연의 주된 원인이 달라, 계절을 섞으면 같은 변수가
계절별로 다른 뜻을 갖기 때문이다. 연도로 자르는 이유는 실제 사용이 "과거로 배워
미래를 맞히는" 것이고, 무작위로 섞으면 같은 날 같은 공항의 다른 편이 학습과
평가에 동시에 들어가 그날의 날씨가 양쪽으로 새기 때문이다.

### 정답 — 10구간

경계 8개 `0 · 15 · 30 · 60 · 90 · 120 · 180 · 300` → 지연 9칸 + 미도착 1칸.
지연은 `ArrDelay`(예정 도착 시각 대비 분)로 잰다.

- 회항했어도 **목적지에 결국 도착한 편**은 `DivArrDelay` 를 지연으로 써서 구간에 넣는다
- **미도착**은 결항과, 회항 후 목적지에 끝내 닿지 못한 편뿐이다
- 지연이 큰 행은 **제외하지 않는다** — 긴 꼬리가 바로 예측 대상이다

### 그날의 유형 — 5가지

`정상일 · 항공사귀책일 · 연결편붕괴일 · 공역혼잡일 · 날씨일`

(공항, 날짜)에 라벨을 붙인다. '실패'는 15분을 넘는 지연 또는 미도착. 그 공항의
그해 여름 평소 수준보다 실패율이 높으면 나쁜 날로 보고, 원인별 지연 분 비중을
그 공항 안에서 표준화해 가장 큰 것을 유형으로 삼는다. 집계에서 **자기 편은 뺀다.**
그 (공항, 날짜)에 **20편 미만이면 라벨하지 않고 그 행을 버린다.**

### 서비스

요구 확률은 **80% 하나로 고정**한다. 손님이 고른 항공편에 대해 25개 조합의
보장 시각을 전부 보여주고, 0.80에 닿지 못하는 편은 **'보장 불가'** 로 표시한다.

### 하지 않는 것

- **클래스 불균형 처리**(가중치·리샘플링) — 모델이 내는 확률이 실제 비율에서
  벗어난다. 우리가 파는 것이 확률 자체다
- **격자 전체 탐색** — 한 번에 하나씩 바꾼다(one-at-a-time)
- **교차검증** — 연도 분할이 시간 순서를 지키는 것이 더 중요하다
- **여러 신뢰수준** — 80% 하나로 고정했다

## 알려진 한계 — 보고서에 그대로 적을 것

**1. MLP와 XGBoost의 차이는 아주 작다 — 예산을 늘려도 뒤집히지 않았다.**
step06 에서 XGBoost 두 설정(기준 depth6 · depth 3)이 400라운드 상한을 다 쓰고
끝났다. 조기 종료(40라운드 인내)가 걸리지 않았다는 뜻이다. 그 여지를 `step06b` 로 측정했다 —
상한만 3000으로 올리고 설정·시드·인내는 그대로 두었다.

| 설정 | 400라운드 | 끝까지 | 멈춘 지점 |
|---|---|---|---|
| 기준 depth6 eta0.05 | 1.351794 | 1.351507 | 최적 580 / 돌린 620 |
| depth 3 | 1.360516 | 1.354709 | 최적 2413 / 돌린 2453 |

둘 다 스스로 멈췄는데도 MLP(1.351091)를 넘지 못했다. 차이가 0.000703 에서
0.000416 으로 줄어든 것이 전부다. 채택은 MLP 그대로이고, `step06c` 가 순위를
확인한 뒤 보정·평가를 다시 돌리지 않았다. 그래서 "MLP가 더 좋은 알고리즘이다"
가 아니라 **"두 계열이 사실상 같은 수준이고 우리 지표에서 MLP가 넷째 자리에서
앞섰다"** 로 써야 맞다.

**2. 보정은 평가 구간에서 완전히 맞지 않는다.**
검증 2025 에서 CDF 보정오차가 0.000000 까지 떨어지는데, 평가 2026 에서는
0.015704 → 0.011507 로만 줄어든다. 적합한 해(2025)와 적용하는 해(2026)가
다르기 때문이다. 보정은 눈금을 완전히 고치는 장치가 아니라 **해가 바뀌어도
남는 치우침을 줄이는 장치**다.

**3. 모델은 낙관적인 쪽으로 치우쳐 있다.**
보정 전 평균 확률이 경계 8개 중 7개에서 실제 비율보다 높았다(최대 +0.0092,
30분 경계). 즉 "제 시간에 올 것" 이라고 과하게 말한다. 보정이 이걸 되돌리면서
평균 보장 지연이 38.9분 → 41.5분으로 **뒤로 밀렸다**. 이게 정직함의 대가다.

**4. 날씨일 칸 두 개는 약속을 지키지 못했다.**
날씨일×날씨일 0.7496, 날씨일×공역혼잡일 0.7843. 날씨가 나쁜 날의 꼬리가
구간 8개로는 잡히지 않는다(보장 불가도 10.6% · 12.4% 로 25칸 중 가장 높다).

**이 한계는 고치지 않고 그대로 보고한다.** 두 칸을 "보장 불가"로 바꿔서 다시
재면 평가 구간의 결과를 보고 서비스를 손본 것이 되어, 연도로 분할한 이유가
사라진다. 측정된 한계를 그대로 적는 것이 이 프로젝트의 결론이다.
